# The old catalogue's schema — tables → collections

TASKS.md 7.1.b. **Status: proven on the mock dump (D42); the real dump's restore
is pending OA9** (the owner's export — a MySQL dump and the product-images
folder, from whoever hosts the old site). Nothing here was read from the old
server: the old site is never logged in to, and its database is only ever a
copy the owner hands over (MIGRATION.md §3).

- [`mock-schema.md`](mock-schema.md) — generated by the harness from the
  restored mock: every table, column, type, key and exact row count, with the
  columns that hold a **secret** (never leaves the container) or **personal**
  data (leaves only for the customer import) flagged. Structure only, never a
  row.
- The mock dump itself and its extraction queries are engine test fixtures:
  `engine/packages/migrate/src/sources/laravel-catalogue/fixtures/`
  (`mock-dump.sql`, `mock-queries/*.sql`). Its case-by-row index is in that
  folder's `README.md`.

## When the real dump arrives (closes 7.1.a)

```sh
cd engine/packages/migrate
pnpm legacy:mysql restore <path/to/dump.sql[.gz]>          # container migrate-legacy-catalogue
pnpm legacy:mysql schema --notes ../../../indies-gallery/content/legacy/schema/catalogue-schema.md --title "Old catalogue schema"
pnpm legacy:mysql tables                                    # every table as JSON Lines, secrets left out
# write indies-gallery/content/legacy/schema/queries/*.sql against the real columns
# (start from the mock's), then:
pnpm legacy:mysql extract --queries ../../../indies-gallery/content/legacy/schema/queries
pnpm legacy:mysql destroy
```

Raw output — `restore.json`, `schema.json`, `tables/*.jsonl`, `extract/*.jsonl`
— lands in `$LEGACY_DATA_DIR/mysql/<label>/`, outside git. What is committed
here is structure and counts: the generated `catalogue-schema.md`, this
mapping (corrected to the real column names), and the extraction queries.
Then re-read the mapping below against the real schema: the mock is modelled
on what the public pages show, and the real one will differ in names, and
probably in tables the public pages never hint at (admin users, carts,
sessions, jobs).

## What the mock proves, and what it cannot

Proven (engine test `restore.integration.test.ts`, run with `MIGRATE_MYSQL_IT=1`,
and the CLI run recorded in the 7.1 report): a plain mysqldump with no
`CREATE DATABASE`, `utf8mb4` text including non-Latin script, a MySQL
zero date, quotes, backslashes and line breaks restores into MySQL 8.4 and
comes back out through SQL unchanged; exact row counts; secrets excluded by
column; every MIGRATION.md §4 dirty-data case present in the extract for 7.2.

Not provable until OA9: the real table and column names, row counts
(~9,500 items, MIGRATION.md §1), how sold history and the unlisted items are
really recorded, whether the dump needs `--database` (a `--databases` dump),
its size and blob tables, and the images folder's naming.
