## Subtasks

- ✅ **8.2.a — the panel on both sites, opened from the header entry point.**
  - `ChatLauncher` (`shared/chat/chat-launcher.tsx`) replaces the disabled placeholder button
    `site-shell.tsx` carried since 4.3; it is a plain button until tapped, then `next/dynamic`
    (`ssr: false`) loads `ChatPanel` — no chat JavaScript, Turnstile script or lexicon ships to a
    page that never opens the chat.
  - The panel streams `delta` text into one assistant entry, shows `status` lines, renders `card`
    events (the shop's `priceLabel` kept distinct from the gallery, which never gets one).
  - The "AI assistant" disclosure (`ChatDisclosure`) is always visible, in the site's copy
    (`lexicon/{en,id}.json`), never model output.
  - 4 suggested starts per site and locale (`suggest.gallery.*`, `suggest.shop.*`).
  - Item and product pages mount `<ChatPageContext title={...} />` (the ticket's one allowed
    "mount/prop line" in each file): a client Context, not a prop threaded through every page,
    since the header and the page are server-rendered siblings under `SiteShell`. The panel shows
    "Asking about: {title}" from this context — but the **id sent to the server is never this
    context**: the panel always sends the current `pagePath`, and the server's own `itemOfPage()`
    resolves the work or product (confirmed against `server/chat/http/message.ts`). The client
    never sends a title, a price or any catalogue fact — only `{ text, locale, pagePath }`.
  - Evidence: `chat-reducer.test.ts` "streams a reply token by token into one assistant entry";
    `chat-disclosure.test.tsx` "shows the AI disclosure"; `chat-client.test.ts` "sends only text,
    locale and pagePath — never a title or a price"; `lexicon/lexicon.test.ts` "each site has at
    least 3 and at most 4 suggested starts".
- ✅ **8.2.b — the handoff card and the lead form behind consent.**
  - `ChatEntries` renders a `handoff` event's button only after `isAllowedHandoffHref()` passes —
    `https://wa.me/`, `mailto:`, or the site's own origin (`siteOrigin()`, passed down as a plain
    prop); anything else is dropped, never shown broken or clickable.
  - The lead form (`ConsentForm`) only renders once the visitor taps "Leave my details" — the
    `lead_form` event just adds that one button; the reducer keeps `leadFormOpen: false` until an
    explicit `openLeadForm` action. Submitting posts `name`, `whatsapp`, `email`, `preferredChannel`,
    `message` and the server's `consentToken` to `/api/x/chat/consent` only — never into
    `sendChatMessage`'s body, which has no such fields in its type.
  - Clear states: rate-limited and budget-exhausted show the server's message plus the retry time
    computed from the response's `Retry-After` header (the stream's own `error` event carries no
    such field — confirmed against `server/chat/http/respond.ts` and `common.ts`); the kill switch
    (`disabled`) shows whatever handoff buttons the refusal already emitted, then the message;
    Turnstile failure and `too_long` show the server's message directly; a network failure shows
    the panel's own `networkError` copy.
  - Accessibility: the log is `aria-live="polite"` (built into `ChatShell`, reused unmodified);
    every control has a label from the lexicon; focus moves to the first focusable element on
    mount; Escape closes (`isEscapeKey()`), and the launcher restores focus to whatever had it
    before the panel opened (`document.activeElement`, saved in `ChatLauncher`).
  - Evidence: `chat-client.test.ts` "renders the server's WhatsApp link and refuses a link to
    another domain" and "contact details go to the consent route, never in a message";
    `chat-entries.test.tsx` (the same, rendered); `chat-reducer.test.ts` "the lead form appears only
    after the visitor asks", "rate-limited shows the retry time", "the kill switch shows the
    handoff"; `keys.test.ts` "matches the Escape key and nothing else".

## Found

- **AI.md §3.5 vs the existing launcher copy.** AI.md says the launcher should read "Ask our AI
  assistant" / "Tanya asisten AI kami". The header's existing lexicon key (`shell.chat`, owned by
  4.3, in `sites/{gallery,shop}/lexicon/{en,id}.json` — not in 8.2's owned paths) already says
  "Chat with us" / "Ajak kami mengobrol". I kept the existing key rather than edit a file outside
  my owned paths; flagging the wording gap for whoever owns that lexicon.
- **No `jsdom` or `@testing-library/react` in this repo.** The ticket's test list includes
  interaction tests ("Escape closes and focus returns to the trigger") that need a real DOM; the
  root `vitest.config.ts`'s `apps` project runs on plain Node (its own comment says jsdom is for
  "once it needs one"), and neither dependency is installed. Adding either touches
  `package.json`/`pnpm-lock.yaml`, which are outside this ticket's owned paths and which
  worker-rules says not to hand-edit. I built the real behaviour (a `keydown` listener calling
  `onClose` on Escape in `chat-panel.tsx`; `ChatLauncher` saves `document.activeElement` before
  opening and restores it on close) and unit-tested the parts reachable without a DOM: the key
  match (`keys.test.ts`) and the reducer/link-allowlist logic. The DOM-interaction test itself is
  not automated here — a `jsdom` + Testing Library addition (or a Playwright pass, which this
  ticket also says not to run locally) would be a separate, owner-approved dependency change.
- **Turnstile needs a callback, not a form-submit read.** The existing widget
  (`sites/gallery/contact/turnstile-widget.tsx`) reads the token from the DOM at form submit; the
  panel needs the token the moment Turnstile mints it, to start the session automatically. I wrote
  a second, small widget (`shared/chat/turnstile-widget.tsx`) in `size: 'invisible'` mode with a
  `callback` option, rather than reuse or modify the existing one (outside my owned paths, and a
  different render mode).
- **No `TURNSTILE_SITE_KEY` check beyond `contact/page.tsx`'s own pattern.** `site-shell.tsx` reads
  `process.env.TURNSTILE_SITE_KEY?.trim() || null` the same way the gallery contact page does; when
  it is unset the panel opens straight into the "unavailable" state (fails closed), consistent with
  `startSession`'s own `deps.turnstile === null` check.
