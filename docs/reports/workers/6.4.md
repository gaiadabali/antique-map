## Transaction boundaries

The webhook verifies and calls the status API **outside** any transaction, then `applyPaymentStatus` opens
**one** READ COMMITTED transaction (`SET LOCAL lock_timeout '5s'`, `statement_timeout '15s'`): `SELECT … FROM
orders WHERE number = $n FOR UPDATE` → pure decision on the locked row → `INSERT INTO payment_events … ON
CONFLICT (dedupe_key) DO NOTHING RETURNING id` (no row = duplicate → commit a no-op, 200) → attempt state →
`UPDATE orders SET status='paid' … WHERE id=$1 AND status='pending_payment'` + history, or the release, or the
staff flag → commit; any throw rolls back the ledger row too and the route answers 500. The sweep reads
candidates in a short transaction, asks the provider with no transaction open, applies each answer through the
same function, then releases in **its own** transaction (status CAS, stock per key in (product, variant)
order, discount use given back, history). `openPaymentAttempt` claims the attempt number under the order's
lock in one short transaction, calls Snap with none open, then stores the token in a second.

## The stock-return SQL (`release.ts`, in the caller's transaction)

```sql
-- 1. the guard: exactly one caller gets a row
UPDATE orders SET status = 'expired', updated_at = $at
 WHERE id = $orderId AND status = 'pending_payment'
RETURNING store_id, discount_code;
-- 2. only if a row came back: per (product, variant) of the order, in ORDER BY product_id, variant_sku
UPDATE stock_levels SET quantity = quantity + $qty, updated_at = $at
 WHERE store_id = $store AND product_id = $product
   AND variant_sku IS NOT DISTINCT FROM $variantSku
```

## Midtrans assumptions (check against the owner's sandbox, OA7)

Signature = hex SHA-512 of `order_id + status_code + gross_amount + serverKey` over the strings as sent
(`"205000.00"`), also on status-API answers; Snap `POST {app}/snap/v1/transactions` (Basic `serverKey:`) →
201 `{token, redirect_url}`; status `GET {api}/v2/{order_id}/status`, `status_code "404"` before a method is
chosen; `expiry {start_time "yyyy-MM-dd HH:mm:ss +0000", unit "minute", duration}`; reopen URL
`{app}/snap/v4/redirection/{token}`; success = `settlement`, or `capture` + `fraud_status accept`.

## Found

1. **TASKS.md 6.4 Owns cannot mount the routes.** Apps may not import `@engine/cms` (eslint
   `payloadImports`), and C13 has every mount re-export `@engine/http/<area>`, which also lists it in
   `ENGINE_ROUTES`. The task owns neither `packages/http` nor `cms/package.json` exports.
2. **COMMERCE.md §13 vs §7 and the brief** — §13 says a payment after expiry re-takes the stock and marks the
   order `paid`; §7 says nothing leaves `expired`. Implemented: stays `expired`, flagged with the amount and
   the action to take (owner re-takes stock or returns the money). §13 needs a staff "restore" action (phase 7).
3. **ARCHITECTURE.md §7 lock order** lists the dedupe row before the order; the order is locked first here,
   because the append-only ledger row must carry its outcome. Deadlock-free (see `apply.ts` header).
4. **`orders` has no paid-amount field**; the amount paid lives in `payment_events.gross_amount` (equal to the
   total by construction — a mismatch is never applied). A `payment.paidAmount` would be a 3.x schema change.
5. **DEPLOYMENT.md §8** lists `MIDTRANS_MODE` as `simulate` or unset; `sandbox`/`production` are now accepted
   explicitly and must match the key's prefix.
6. COMMERCE §6 step 5 (notification jobs in the same transaction) and "rate-limited" are not built: no jobs
   are registered yet and no shared limiter exists.
