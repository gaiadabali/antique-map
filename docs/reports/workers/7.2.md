## What this ticket built

A custom Payload admin view at `/admin/orders` (and `/admin/orders/{id}`), registered once in
`engine/packages/cms/src/registries/views.ts` as `{ name: 'orders-panel', value: { path: '/orders/:id?', Component:
'@engine/cms/admin/orders#OrdersPanelView', exact: true } }`. One view, branching on `req.user.role`:

- **Store role** — a phone-first queue (New / In progress / Delivered today) and an order screen: items, address,
  a Google Maps link, the buyer's WhatsApp, the gift note, the one big next-status button (its label and whether
  it is enabled come from `judgeMove`, never invented here), the camera-friendly driver-image upload, and "Can't
  send this" (hand back with a reason).
- **Owner/editor role** — a filterable list (status, store) and an order screen with forward/backward moves,
  reassign (a store picker, filtered to active stores able to fill the order — the core still refuses
  `not_enough_stock`), cancel with a reason, and a "needs you" marker on `needsAttention`.

**Every action is a plain HTML form or link — no client JavaScript on the critical path.** The confirm sheet
CONTENT-OPERATIONS.md §5.1 asks for is a `?confirm={status}` query step rendered server-side (classic
post-redirect-get), not a client modal. This was a deliberate simplification for this ticket's speed target (a
first-timer completes the flow unaided, two taps per step) and because the cms package does not type-check or
bundle JSX the ordinary way (see Files): the fewer moving parts client-side, the less there was to get wrong
without type-checking. If a later ticket wants an optimistic/animated confirm sheet, the server-rendered one here
is the fallback to keep.

## Found (defects/decisions, not mine to fix)

1. **`request.url` inside an app route handler, behind this project's host proxy, is the internal single-host URL
   (`localhost:…`), not the browser's virtual host (`shop.localhost`, `oldeastindies.com`).** My first cut of the
   move/reassign/hand-back/driver-image routes built their redirect with `new URL(path, request.url)` —
   `Response.redirect(url, 303)` — which sent the browser to `http://localhost:4315/admin/orders/{id}`, a 404 on
   that host. Fixed by redirecting with a **relative** `Location` header instead (`new Response(null, {status:
303, headers: {Location: ...}})`), which needs no host at all. This is a sharp edge for **any** future route
   that redirects behind the proxy — worth a line in CONVENTIONS.md or ARCHITECTURE.md's rendering section, since
   nothing in the 404 pointed at the cause (no server-side error — Payload's own `notFound()` boundary rendered,
   and only a captured network trace showed the wrong host in the `Location`).
2. **`fixtures.ts`'s stores (`E2E-A`, `E2E-B`) are made `{ code, name }` only** — inactive, no address, no pin.
   That's fine for the roles drive (3.6), but `reassignOrder`'s `store_unavailable`/`not_enough_stock` and the
   database's `stores_active_has_address_and_pin` constraint both need an active, pinned, stocked store. My own
   `store-panel-fixtures.ts` activates and pins both fixture stores and adds a stock-levels row for the product,
   rather than touching the shared `fixtures.ts` (not mine). If another phase-7 ticket also needs reassignment
   against the shared fixtures, this is worth folding into `fixtures.ts` itself.
3. **Payload does not parse a registered view's named path segment.** With `path: '/orders/:id?'`, I expected
   `props.params.id`; what actually reaches a plain custom view (one that doesn't override a built-in `viewKey`)
   is `props.params.segments`, the catch-all route's raw array (`['orders']` or `['orders', '123']`) —
   `getCustomViewByRoute` in `@payloadcms/next` returns only `{ payloadComponent }`, no parsed route params. I
   read `segments[1]` directly in `view.jsx`; worth naming if another ticket registers a parameterised custom
   view.
4. **A registered custom view that isn't overriding a built-in `admin.routes` key gets no `templateType`**
   (`getRouteData.js`'s `case 1`/default-fallback paths), so Payload never wraps it in `DefaultTemplate` — no nav,
   no header. I did not add it back (the phone-first speed target argues for a minimal shell, and CONTENT-OPERATIONS
   §5.1 says nothing about keeping the sidebar); the view supplies its own "← Back" link instead. If the owner
   wants the full admin chrome around `/admin/orders`, that is a `<DefaultTemplate>` wrap in `view.jsx`, not a
   redesign.
