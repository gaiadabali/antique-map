## Found

- **The ticket's literal folder names (`{makers,places,stories,about,guarantee}`) are not what the
  proxy actually rewrites to.** `parsePublicPath()` (`@engine/config/sites`'s
  `routes/parse.ts`) rewrites every surface to `SURFACE_ROUTES[surface].internal`
  (`routes/surfaces.ts`): `maker/[slug]`, `place/[...path]`, `story/[slug]`, `page/[slug]` — the
  *internal* canonical names, not the localised public segment (`makers`/`pembuat`,
  `places`/`tempat`). A folder literally named `makers/` would never be reached: the proxy already
  rewrote the request to `/gallery/en/maker/…` before Next's router sees it. I built the routes at
  the internal names instead, confirmed by the `pnpm build` route listing
  (`/gallery/[locale]/maker`, `/gallery/[locale]/place`, `/gallery/[locale]/page/[slug]`,
  `/gallery/[locale]/story/[slug]`) and by `routes.test.ts`'s own round-trip cases
  (`['maker', {}]`, `['page', { slug: 'about' }]`). The shop's own `collections/[slug]` folder
  (plural) looks like the same mistake already shipped and unreachable in production — not mine to
  fix, flagged here since it's the same class of bug.
- **The `pages` collection has no "blocks" yet.** The ticket's step 4 asks for "one small renderer
  per block type the collection defines (prose, figure, work rail, FAQ, call to action)". Reading
  `engine/packages/cms/src/collections/pages/index.ts`: `body` is `type: 'textarea'` (plain text),
  with its own admin note, *"Plain text for now. Rich-text blocks come with task 9.3."* There is no
  block field to switch on. I rendered the two kinds the schema actually offers — prose
  (`intro`/`body`, paragraphs split on blank lines) and a work rail (`works`, through the
  catalogue's own card projection) — and left figure/FAQ/CTA unbuilt rather than invent dead
  renderers for fields that do not exist. Re-visit with 9.3.
- **`pagePublishGuard` (`engine/packages/cms/src/collections/pages/publish-guard.ts`) reads
  `data.title` as a locale-keyed object (`data.title.en`)**, which only a `locale: 'all'` save
  produces — a plain `payload.create({ data: { title: 'X' } })` under the default locale leaves
  `data.title` a bare string, so `.en` reads `undefined` and every publish refuses with "needs a
  title in English," even with a title. Not this ticket's file to fix (`publish-guard.ts` isn't
  under `server/gallery/pages/**`), so the db test and the e2e seed both publish with
  `locale: 'all'` and locale-keyed field values instead, which the hook accepts. Worth a follow-up
  ticket against the collection itself — any other caller publishing a page under a plain default
  locale save hits the same refusal.
- **TASKS.md's 5.4.b bullet names "contact" as in scope; the ticket brief says it is not** ("`/
  contact` and `/sell-to-us` are not yours (5.3)"). I followed the ticket brief (the more specific,
  current instruction) and built no `/contact` route.
- **The shared dev Postgres container was mid-crash-recovery for this entire session** —
  `indies-platform-dev-postgres-1`, `syncing data directory (fsync)`, climbing past 1100 seconds,
  evidently from another worktree's load, not anything this session did. It blocks exactly the
  pieces of evidence the ticket's Verify section needs live (the db tests, the manual curl checks,
  the e2e run, the fresh-clone re-run). Everything that does not need a database — typecheck, the
  full non-db vitest suite, lint, format, `check:generated`, `check:tokens`, `tasks:lint`,
  `tasks:check`, the production build — is green.
