### The db test suite: an environment blocker, not a code defect

Every `*.db.test.ts` under `engine/apps/web/src/server/analytics/dashboard/` and
`engine/packages/cms/src/admin/dashboard/` — **including run 1's three pre-existing files
(`panels.db.test.ts`, `visitors.db.test.ts`, `render.db.test.ts`), which this ticket did not
touch** — fails identically at the very first step, `CREATE DATABASE`, with `Error: Connection
terminated unexpectedly` from `pg-pool`. That this breaks tests my branch never changed is the
tell: this is the host, not the diff.

I spent real effort isolating it before giving up on running the suite here, because the ticket's
restart note already flagged this workstation as resource-short:

- `pnpm db:fresh` (no `DATABASE_URL`/`CMS_TEST_POSTGRES_URL` involved at all) fails the same way
  against this worktree's own suffixed database.
- `docker ps` shows the dev Postgres container healthy, and `docker exec … psql -c "SELECT 1"` and
  even `docker exec … psql -c "CREATE DATABASE …"` **succeed** when run *inside* the container —
  proving Postgres itself is up and able to do the work.
- A raw TCP connect from Node to `127.0.0.1:5432` (bypassing `pg` entirely) connects cleanly.
- Sending an actual Postgres wire-protocol `StartupMessage` over that raw socket gets **no response
  at all** — the socket is closed (a clean FIN, not a reset) within ~35 ms of the write, before
  Postgres's own log shows any trace of the attempt (`docker logs --since 5m` is empty across
  several attempts). So the connection is accepted and then dropped by something *between* the host
  and the container — not refused by Postgres, not an auth failure (`pg_hba.conf` has `host all all
  127.0.0.1/32 trust`, so a wrong password could not cause this either).
- `C:` is at 99% (938 G / 952 G used, 15 G free), and the container's own startup log (from earlier
  in its 34-hour uptime) shows 150–230 **second** `fsync` calls during a checkpoint, `autovacuum
  worker took too long to start`, and intermittent `could not send data to client: Broken pipe`
  entries — i.e. this host is under exactly the I/O and memory pressure the restart note described,
  and the many leftover `cms_*_test_*`/`cms_claim_scratch_*` databases from other concurrent worker
  sessions (dozens, from `\l`) corroborate that several other sessions are hammering the same
  container right now. The most consistent explanation is Docker Desktop's host-side port-forwarding
  proxy dropping the connection under that load — not a `max_connections` limit (9 of 100 in use)
  and not anything in this ticket's diff.

Per the worker rules ("the shared dev Postgres is busy… if the database is unreachable, stop and
report it; do not try to fix it. Never manage the dev stack's containers"), I did not touch the
container, retried the actual suite several times (consistently reproducible, not flaky), and did
not spend further time chasing a host-level Docker networking issue. I left no probe scripts behind
(`probe-create-db.mjs`/`probe-raw.mjs`, used only for the diagnosis above, were deleted before this
commit) and did not run `pnpm db:fresh` to completion for this worktree (its suffix database was
never created, so nothing was left to clean up).
