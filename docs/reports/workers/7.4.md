Found
1. **F1 (fixed, test-only):** the tracking page carries two "Ask on WhatsApp" links — the order's own
   (inside the "Order #" region) and the shop's generic footer one — so
   `getByRole('link', { name: 'Ask on WhatsApp' })` was a Playwright strict-mode violation. Scoped to
   `page.locator('main')` in the test. Not a product defect — this is the page's real, intended shape.
2. **F2 (fixed, test-only):** the admin's order view renders with no `main` landmark, so
   `page.locator('main p').first()` (reading the store name shown on an order) never resolved. Reads the
   first paragraph following the "#&lt;number&gt;" heading instead
   (`orderHeading.locator('xpath=following::p[1]')`).
3. **F3 (environment, reported, not fixed — outside owned paths and worker rules forbid touching shared
   services):** partway through this ticket's verification runs, the shared dev Postgres
   (`indies-platform-dev-postgres-1`) began answering `FATAL: the database system is in recovery mode`
   (Postgres code `57P03`) and, on later attempts, `Connection terminated due to connection timeout` —
   alternating between the two for roughly 30 minutes straight, across many retries, with nothing run here
   that would restart or reset it. `docker`/process inspection commands were blocked by this session's own
   sandbox (`tasklist`, `Monitor` on a log tail), so the cause could not be identified from this worktree;
   the orchestrator should check what else was running against this container around 2026-10-05 ~22:55-23:30
   (server time from the task's own timestamps) — another worker's `db:fresh`, a container restart, or a
   resource limit are the likely candidates.
4. Email check (`findOrderEmail`, reused verbatim from `tests/e2e/shop/gate.spec.ts`'s own pattern)
   intermittently timed out at 15s against Mailpit even though a direct `curl` to the same URL moments
   later answered 200 — plausibly the same host contention as F3, not a spec bug.
