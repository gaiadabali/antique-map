## Found

- **A production build's tracking 404 carries two `meta[name="robots"]` tags**, not one: the matched route's own
  static `metadata` export (`content="noindex, nofollow"`, `track/[token]/page.tsx`) plus a second Next adds on
  its own `notFound()` escape hatch (`content="noindex"`). Both say `noindex`, so nothing is mis-indexed, but a
  test (or anything else) assuming exactly one tag will break. Only visible on a production build, not `next
  dev` — the prior run's e2e case asserted on the first/only match, so this had never been exercised until this
  ticket actually ran a production build. Fixed in the test (checks every tag); not a page bug.
- **`pnpm db:fresh` failed once with a bare connection error, then succeeded immediately on retry** — looked
  like a transient Postgres hiccup on this machine, not a real migration problem (the same migration ran clean
  the second time).
- **A `notify.db.test.ts` run under `--maxWorkers=1` failed its `afterAll` teardown with `ECONNRESET`** dropping
  its own temp database, after all 3 of its tests had already passed; re-run alone, it passed clean including
  teardown. Looked transient (Postgres connection reset under load from the rest of the suite running
  alongside), not a regression — nothing in this ticket touches that file or its fixtures.
- **Standing up this ticket's own e2e run needed hand-wiring an environment** `next start` doesn't get from this
  worktree's `.env.local` (that file lives at the repo root; `next start`'s own env-file loading only reads the
  app's directory, `engine/apps/web`) — `GALLERY_HOSTS`, `SHOP_HOSTS`, `DATABASE_URL`, `PAYLOAD_SECRET` as a
  temporary `engine/apps/web/.env.production.local`, deleted after. Worth a line in `docs/WORKFLOW.md` or
  `.env.example` for the next worker who needs a real e2e run rather than `pnpm build`'s static-only smoke.
