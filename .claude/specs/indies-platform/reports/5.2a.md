**Found (doc contradictions / decisions the lead should know):**
1. **The ticket's default width ladder contradicts the media contract (C9).** The ticket says "Default widths `[320, 640, 960, 1280, 1600, 2400]`"; `contract.ts` pins `DERIVATIVE_WIDTHS = [320, 640, 1024, 1600, 2400]` as "the width ladder … the image loader picks from" and `SAVE_DATA_MAX_WIDTH = 1024`. Emitting 960/1280 would be dead artefacts and omit the 1024 rung the loader asks for. I used the contract ladder as the default (`widths` option can override).
2. **The ticket's signatures cannot name contract keys — they lack the `AssetId`.** `derivativeKey(id, width, format)` and `iiifPublicKey(id)` both need a content address that `makeDerivatives`/`makeTiles` are never given. I added one optional field to each options object (`id?: string` / `iiifId?: string`): given, keys are the full contract naming and `info.json`'s `id` is stamped; without, keys are the asset-relative part (`<width>.<format>` / pyramid paths) and the upload hook composes the full key. No new scheme invented.
3. **Sharp's iiif3 tile layout needs the pipe form** (`sharp(input).pipe(sharp().tile({...})).toFile(base)`); calling `.tile()` on the input pipeline directly silently writes one flat image instead of a pyramid. The temp-dir layout is `{region}/{size}/{rotation}/{quality}.jpg` plus `info.json`; tiles are JPEG (Level 0 tiles are a delivery format; the master holds the pixels). `info` is the parsed `info.json`; its `id` still points at sharp's default `https://example.com/iiif/…` unless `iiifId` is passed — the upload hook must point it at `iiifInfoUrl(MEDIA_PUBLIC_URL, id)` before upload (contract C9: "Each info.json `id` is its final public URL").
4. **AVIF is reported as the `heif` container** by `sharp().metadata()`; the library's format guard and tests account for it.
