## What to build
1. **Schema** (regenerate types after):
   - `partners.productsCarried` becomes a `relationship` to `products`, `hasMany` (drop the text field and its
     "3.3 relates this" note). Keep the label.
   - `leads.partner` — optional `relationship` to `partners` (sidebar), "the partner created from this lead".
   - `leads.closedAt` — a `date`, read-only in the admin, stamped by the existing `appendStatusHistory`
     `beforeChange` hook when status becomes `closed` (cleared if reopened). Retention counts from it.
2. **The lead service** `server/leads/`: `createLead(deps, input)` where `input` is a zod-free validated shape
   (`kind`, `site`, `source`, `name`, `whatsapp?`, `email?`, `preferredChannel?`, `message`, `locale`,
   `consentVersion`, `items?`) with one shared validator `parseLeadInput(unknown) → { ok, value } | { ok:false,
   errors: Record<field, lexiconKey> }` (at least one of whatsapp/email; WhatsApp `+` international; lengths
   from the collection). Ports: `verifyTurnstile`, `allow(ipKey)` (in-memory: **10 posts a minute per IP**,
   SECURITY.md), `store.create`, `notify`. `createLead` checks Turnstile → rate → validate → creates through the
   Local API (`overrideAccess: true` is required — public create is refused by design; comment why) → sends the
   owner a **"new lead" email** (`notify`): subject with kind and site, body with the kind, site, a link to the
   lead in the admin (`ADMIN_HOST` origin + `/admin/collections/leads/{id}`), **no message text and no contact
   details in the email** (the owner opens the admin). A failed email is logged and does not fail the lead.
   The owner's address comes from `site-settings` (whatever field holds the contact email; a marked placeholder
   if none). Also export `notifyNewLead` so chat's hand-off can call it later (do not edit chat).
3. **The partnership submit**: a server action in `sites/shop/partnership/action.ts` (`'use server'`) calling
   `createLead` with `kind: 'partnership'`, `site: 'shop'`, `source: 'form'`; a small client island
   `PartnershipForm` (useActionState) replacing the disabled placeholder form in `partnership.tsx` — same
   fields plus WhatsApp, a consent line with its version, the Turnstile widget (site key from env; follow how
   the chat widget loads it), inline per-field errors from lexicon keys, a success state, and a disabled button
   while pending. Copy in the shop lexicon, `en` and `id`. Tokens and shared components only.
4. **The retention sweep** `cms/src/jobs/retention/`: `runRetention(payload, now: Date, policy =
   RETENTION_DEFAULTS)` — pure over the Local API, returns counts `{ chatSessions, leads, driverImages }` and
   logs only those counts (no ids, names or contacts). Defaults from COMPLIANCE §1, each a named constant:
   chat sessions whose `lastMessageAt` (or `expiresAt` if set) is more than **30 days** before `now` → deleted;
   leads with `status: 'closed'` and `closedAt` older than **24 months** → deleted (leads not closed are never
   touched; `spam` leads older than 30 days → deleted too, and say so in the report); orders delivered or
   cancelled more than **30 days** ago that still hold a `driverImage.key` → the private object deleted and the
   group cleared (the order itself stays). Batch in pages; idempotent (a second run deletes nothing).
5. **The cron route** `POST /api/x/cron/retention` behind `refuseCron`, the sweeps pattern, loading Payload
   by `import()` only after auth; answers the counts as JSON. Add one line to the report naming the crontab
   entry the orchestrator must add on the host (daily, 03:15 WITA).
