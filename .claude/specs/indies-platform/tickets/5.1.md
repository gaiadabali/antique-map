## What to build
1. **Loaders (5.1.a)** in `server/gallery/catalogue/`:
   - **The listing**: paginated, sorted (`newest` · work date old→new · new→old · maker A–Z — the fuzzy
     reading orders the date sorts), filtered by the six facets below, each facet returning **counts that
     apply every filter but its own** (otherwise unselected options all read zero).
   - **Facets**: availability (`works.status`; the default query is `available` + `on-hold` and the page
     offers a visible "Include sold" toggle — the sold archive is a feature, never deleted), type
     (`objectType`, the fixed list), maker (counts; an alias spelling resolves to the maker — Valentyn →
     Valentijn), place (the `parent` tree: island group → region → town; **counts roll up to ancestors**;
     one primary place per work), period (century chips plus a from–to year pair, number inputs — never a
     slider alone), subject (terms kind `subject`).
   - **Search (5.1.c)**: one `searchWorks` that matches titles (hook and original) and their accents away
     (`unaccent`), maker names and aliases, place modern **and historical** names, subjects, and stock
     numbers. A term that names a place — modern or historical (Batavia, Celebes, Buitenzorg) — widens to
     that place **and its descendants**, so "Celebes" and "Sulawesi" find the same works. `pg_trgm` gives
     exactly **one** "Did you mean" suggestion on a near miss. A stock-number query (`M.0500`, the gallery's
     pattern) jumps to that item. A plain `ILIKE`/direct-query approach is acceptable where the FTS
     configuration is not yet on the table — **say so in the report**; the derived `search_documents` table
     (ARCHITECTURE §9) is deliberately **not** this ticket's work — leave a `// TODO(search-documents)` note.
2. **Pages (5.1.b)** under `app/(gallery)/gallery/[locale]/`:
   - **Browse**: `objectType` and `place` are **path segments** with the per-locale vocabulary slugs from
     `SITES.gallery.routes` (`/browse/antique-maps`, `/jelajah/peta-antik`); every other facet is a query
     param, so a filtered page has a URL. Facet chips as real links; applied-filter chips above the grid.
     **Cards**: the image on its mat — contained, never cropped — title, maker and date with their precision,
     dimensions, and one status line (*Price on request* · *On hold* · *Sold*). One card is one link, to the
     item route via `publicId` (the item page itself is 5.2 — link to its route shape; a 404 until 5.2 lands
     is expected). **Phone (390 px)**: a two-column grid, facets in a bottom sheet, a live count on Apply
     ("Show 34 works"), sticky Apply and Clear. **Desktop (1280)**: facets in a left column, the grid in
     four columns. A filter with zero matches never hides itself — it shows its zero (EXPERIENCE §9).
   - **Search**: the query from `searchParams` inside `<Suspense>`; results as the browse cards; a plain
     no-results state with an **Ask us** handoff (WhatsApp/email from the lexicon and site settings — never
     a price, never a deal); one "Did you mean" line when trigram has a candidate.
   - `generateMetadata` through `@/server/seo` (`pageMetadata`); no price in any meta.
3. **Wiring the beacon (already on `main`)**: the pages emit `page.viewed` (`pageType: 'listing'` /
   `'search'`), `listing.viewed` (with facets and resultCount) and `search.submitted` (query redacted by the
   beacon, never raw in a URL you build) through the existing `shared/beacon` — read how the shop pages call
   it; do not invent a second mechanism.
