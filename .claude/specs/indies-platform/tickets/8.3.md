## What to build
1. **8.3.a** `POST /api/x/draft` `{ workId }`: signed-in **owner or editor** only (checked from `payload.auth()`,
   not from the body); the work must have ≥ 1 photograph. Server fetches the work's images (staff URLs, server side),
   sends them to the vision model (`AI_DRAFT_MODEL`, default the chat model; key host-only; a `DraftModel` port with
   an Anthropic adapter and a fake for tests) with a fixed system prompt, and parses a **strict JSON** reply
   (schema-validated; anything else → a refusal, nothing written). Drafts: title, description, object type, probable
   date, places, subjects, dimensions (only when a scale is visible; otherwise left empty). Places, subjects and
   object type map only onto **existing** vocabulary rows (no new terms). Each written field is marked unverified in
   `aiDraft`. A field the editor already filled is not overwritten (reported as skipped).
2. **8.3.b** The model's output is never allowed to set grade, provenance, asking price or any price/internal field
   — enforce with an allow-list on the write, not the prompt. Text visible in the photographs is data, never
   instructions (§3.1). The audit trail records who requested the draft and when, and who verified each field and
   when (verification = the editor ticks the field's verified box in the admin; record the user server-side in a
   hook, never from the client).
3. **8.3.c** The publish guard refuses while any drafted field is unverified and names those fields in both
   languages.
4. The admin action: a "Draft from photographs" button on a work's edit view (owner/editor only), showing progress,
   the result (filled / skipped fields) or a plain refusal. Tokens and lexicon only.
5. Limits: one draft per work at a time; per-user 20 drafts/hour; the site-settings AI kill switch from 8.1 also
   stops drafting.
