## Findings

1. **should-fix (SCH, with or right after 4.6)** — `engine/packages/cms/src/db/probe.ts:25`. **A timed-out probe returns a dead client to the pool, and the health probe keeps putting it back.**

   **The mechanism.**
   - `databaseProbe()` always calls `client.release()` with no argument.
   - pg 8.20.0's `query_timeout` (`lib/client.js:640-660`) rejects the caller, but it leaves the connection's active query in place.
   - So on a connection that has gone dark (a partition, a NAT drop, a failover), that client goes back to the pool looking idle. Every later query on it waits behind the dead one and times out too.
   - Drizzle's own queries go through `pool.query`, which releases with the error and so destroys the client. The probe path does not.
   - As a result, each health check that draws the zombie re-pools it. The next page loader to draw it hangs for `QUERY_TIMEOUT_MS` (60 s) before failing.

   **Evidence.** `scratchpad/r46/zombie.mjs` uses a pg Pool (`max: 1`, `query_timeout: 1000`) through a TCP proxy that can darken established connections. It runs `probe.ts`'s exact shape:

   | Probe | `release()` | `release(error)` |
   | --- | --- | --- |
   | healthy | ok, 22 ms | ok |
   | connection dark | `Query read timeout` | `Query read timeout` |
   | network healed | `Query read timeout` | ok, 20 ms |
   | again | `Query read timeout` | ok |

   **Fix.** `client.release(failure)` when the query throws. This is the third bullet of the independent 4.8 review's S3; it was left out of 4.8.e's Owns. Add a db test in which a query that times out destroys its client.

   **Severity.** Rare on Helios, where Postgres is local, which is why it does not block. But `/api/health` is now what exercises the probe once every 5 s.

2. **should-fix (DEPLOYMENT §3, 5.1 — HAR and the owner)** — `health/payload-ports.ts:80`. **The first health check lasts as long as the migrations, and nothing documents how long the deploy agent waits.**

   **Why `cms()` is untimed.** A first call that is migrating must not answer 503, or it would roll the release back. Every concurrent check joins that one flight: in my race, both first checks answered 200 in 0.65–0.72 s, one having migrated and one having waited on the lock.

   **What bounds the wait instead.**
   - The pool's 5 s connect timeout: against a black hole, I measured 503 in 5.46 s.
   - The adapter's 60 s ceiling per statement.
   - The deploy agent's own patience, which is the part nobody has written down.

   DEPLOYMENT §3 checks `https://<domain>/api/health`, through Cloudflare, whose proxied requests end at 100 s with a 524. The agent's own timeout and retries (gaiada-poll) are recorded nowhere. So a migration longer than either would roll back mid-migration, and pm2's reload would then kill the migrating process.

   **Fix.**
   - Record the agent's health timeout and retry count in DEPLOYMENT §3.
   - State that the first check blocks for the duration of the migrations, and that a release whose migrations may run past that bound is migrated before the reload (§4's manual `pg_dump` step is the natural place).
   - Alternatively, have the agent check on loopback, `http://127.0.0.1:<port>/api/health`, which is not subject to Cloudflare's 100 s.

3. **should-fix (5.1.a's crontab)** — `cron/jobs/route.ts:41-46, :49, :57`. **409 `busy` needs the crontab to treat it as success, and a run that never settles holds it for good.**

   The single-flight is correct: a per-process promise is exact under DEPLOYMENT §3's `fork` / `instances: 1`. Auth comes before the busy check, so an anonymous caller cannot probe it. A crontab `curl -f` would still exit 22 on every tick of a long run, and cron mails the site user each time.

   `running` clears only when `jobs.run` settles. A task awaiting a hung upstream therefore makes every call answer 409 until the process restarts. Health does see it: `stalled` counts `processing` jobs whose `updatedAt` is more than 10 minutes old. Nothing in the jobs route says so, though.

   **Fix.**
   - 5.1.a's line treats 200 and 409 as success, for example `curl -sS -o /dev/null -w '%{http_code}' … | grep -qE '^(200|409)$'`. Or the route answers 200 `{ busy: true }`; the 4.1 review allowed either.
   - Put the run's start time in the 409 body (`{ busy: true, since }`), and log once when a run passes, say, 10 minutes.

4. **nit** — `health/payload-ports.ts:71-74`. **An empty database reports `database: error`, not `unmigrated`.**

   On an empty database with no `payload_migrations` table (`r46_empty`, no `RUN_MIGRATIONS`), the count throws `Failed query: select count(*) from "payload_migrations"`. So the answer is 503 `detail: 'error'`. The `unmigrated` branch fires only for a table that exists with no rows. It fails closed either way, but S4's case, a database that no migration ever reached, is exactly the missing table.

   **Fix.** Map `42P01` (undefined_table) to `unmigrated`, or ask `to_regclass('payload_migrations')` first. Add a test.

5. **nit** — `health/route.ts:35-38`. **Two paths answer Next's bare 500 instead of the JSON 503.**
   - `load().then(onLoaded, onFailed)` does not catch a throw inside `onLoaded`: a module without `payloadHealthPorts` becomes a rejected check, and so a bare 500 from Next.
   - The same happens to a throw from `ports.log` in `checkHealth`.

   The status still fails closed for the rollback, but the body is not the designed one. **Fix:** `.then(onLoaded).catch(onFailed)`, and wrap `checkHealth` so that any throw becomes the 503 body.

6. **nit** — `health/health.ts:78-79` and `health/queue.ts:82-84`. **The public body carries operational counts.**

   It carries:
   - `boot.problems` and `warnings` (41 on the test brand);
   - the queue's `pending`, `lagSeconds` and `stalled`.

   Nothing is secret, and it never echoes a finding's text, a version or a path. I judge it acceptable. The counts do tell an outsider that the queue is backed up, or how misconfigured a host is. The deploy agent needs only the status code, and only Alloy on the box needs the numbers.

   **Optional fix:** send the counts only to a loopback caller (no `X-Forwarded-For`), and the checks' `ok` and `detail` to everyone. This is the same point as the 4.1 review's #13.

7. **nit (MED, before the first heavy task)** — `cron/jobs/payload-queue.ts:21`. **One run executes up to `limit` jobs at once.**

   `payload.jobs.run({ limit, allQueues: true })` passes no `sequential`, so `runJobs` runs the claimed batch with `Promise.all`: up to 10 jobs at once by default, and 100 at `CRON_JOBS_LIMIT`'s cap, all inside the web process. ARCHITECTURE §10 moved the queue off `autoRun` precisely because tiling competes with renders.

   Separately, `STALLED_AFTER_SECONDS` (`queue.ts:18`) will report a single-step task that runs longer than 10 minutes as `stalled`. It is only reported, never gating.

   **Fix.** Decide this when MED registers derivatives. Either `sequential: true`, or a low default limit with heavy tasks on a queue of their own and `concurrency` set.

8. **follow-up (8.2.e, 33.3.e)** — **The in-request invalidation from a jobs run is valid, and still unexercised.**

   **Why it is valid.**
   - `payload.jobs.run` builds its `req` with an empty `context`. So a task's hooks carry no collector, and `invalidate()` takes the `after()` path inside the cron route's request.
   - `after()` from a route handler is proven on this production build (#10 below).
   - The callbacks run once the whole run has answered, after every job's own commit.
   - `batch.context()` is for the `payload jobs:run` worker, never this route. The route must never create one, since nothing would flush it.

   **Why it is untested.** No task is registered yet: `jobs.enabled` is false, and the route answered `{"detail":"no-tasks"}` live.

   **One case to prove at 33.3.e.** On every deploy, `/api/health` is the first caller of `cms()`. So the Payload instance, and with it the hooks' module copies of `@engine/cache` → `next/server`, come from the health route's chunk. The first hook proof should save through `/admin` *after* health has initialised Payload, to show that `after()` finds the admin request's store across route bundles.

9. **nit** — `revalidate/body.ts:60, :80`. **Two refusal messages could say more.**
   - **Oversize.** A body past 64 KiB is refused as "not UTF-8 within 65536 bytes"; "larger than 65536 bytes" would say what happened.
   - **Unknown kind versus malformed.** Both read `tags[i] is not a tag @engine/cache makes`. For the outbox (the 4.8 review's N5), the first can be retried: it is a web process older than the worker during a deploy. The second is a bug to alert on.

   All-or-nothing per body is C13's rule, and it loses nothing: `postTags` rejects with `accepted`, and the collector keeps the rest. But the caller cannot tell the two cases apart.

   **Fix.** Distinct reasons, still quoting only the position, such as `tags[3]: unknown kind` versus `tags[3]: malformed`.

10. **nit (evidence, recorded)** — `revalidate/route.ts:16-19`. **A 204 means scheduled.** `after()` runs its callbacks once the 204 has gone out. A request that arrives in that instant can still read the old entry.

    The route's comment records this as an invariant (the 4.8 review's N5), and it is exact while the `'use cache'` store is in memory. A persistent `cacheHandler` would need the route to expire before answering. No change is needed.

### Failure modes and security probes (production builds)

**Health**

- **A hung query.** `LOCK TABLE payload_migrations IN ACCESS EXCLUSIVE MODE` was held for 15 s.
  - The first check answered 503 `database: timeout` at 2.52 s; checks inside the memo took 5 ms.
  - The next check awaited the *same* pending query: another 2.5 s, with **one** active session of three throughout, so no client per check.
  - Once the lock was released the answer stayed 503 for the rest of the memo window, then 200. A failure is kept for ≤ 5 s, which is by design.
- **A black-hole database.** `cms()`'s connect gave up at the pool's 5 s: 503 `database: error`, `queue: no-database`, in 5.46 s. The log names the cause and never the URL: `grep postgres:postgres` found 0.
- **Sessions killed under a live server** (`pg_terminate_backend`): health stayed 200.
- **Methods and headers.**
  - `HEAD` answers 200; `POST` answers 405.
  - `no-store` and `nosniff` are present.
  - No `Accept-CH` or `Critical-CH` on the API (4.1 #11 holds).

**Revalidate**

- **Body cap.**
  - A chunked 10 MB body with a good bearer: 400 after 10 ms.
  - A declared 100 MB `Content-Length`: 400 before a byte was read.
  - A 1 KB-every-50-ms trickle: cut off at exactly 65,536 bytes (400 at 3.5 s).
  - A chunked 10 MB body with a wrong bearer: 401 in 4 ms, body unread.
- **JSON.**
  - `{"__proto__":{"tags":[…]}}`: 400 `tags is not a list`. `JSON.parse` makes an own property, and nothing is read through the prototype.
  - Duplicate `tags` keys: last one wins (204). No producer emits them.
  - 32,000 levels of nesting inside 64 KiB parse in 5 ms (V8's parser is iterative).
  - A non-string tag: 400.
- **Refusals** quote a position, never the value.
- **Methods:** GET answers 405.

## Checked and correct

- **The bearer** (`shared/bearer.ts:19-31`), used by both cron and revalidate.
  - It compares `timingSafeEqual` over two SHA-256 digests, 32 bytes against 32, so neither the secret's length nor its prefix leaks.
  - It compares the whole `Bearer <secret>` header, so `bearer`, a double space or a trailing byte gets 401. Multiple `Authorization` headers are joined with `, ` and fail.
  - The secret is trimmed as the boot check and `postTags` read it.
  - It is checked before the body (the test asserts `bodyUsed === false`; live, a 10 MB body got 401 unread).
  - Both secrets must be at least 32 characters once deployed (`boot-check/platform.ts` STRONG).
  - No cookie authenticates either route, so neither needs CSRF protection. Neither sends CORS headers, so a browser cannot send the bearer cross-origin (preflight fails).
- **Health semantics.**
  - Only app, boot, database and storage gate. The queue is `degraded`/200, whether it lags, stalls or throws, and a failed gate is 503 whatever the queue says (`health.test.ts:141-168`).
  - One probe per check, and the boot check re-reads that answer (`payload-ports.test.ts:52-61`).
  - A thrown database port keeps its cause as a rethrowing probe, redacted into the log and never the body (the 4.1 review's #1).
  - The memo keeps values, not rejections. `bounded` never leaves an unhandled rejection: `query.then(clear, clear)` observes the late settle, and the timer is cleared in `finally`.
- **The queue filter** is `runJobs`' own in 3.90.2 (`runJobs/index.js:24-52`): `completedAt` does not exist, `hasError ≠ true`, `processing = false`, and `waitUntil` is absent or in the past, with no `queue` term, matching `allQueues: true`. Lag counts from `max(createdAt, waitUntil)`.
  - `stalled` keys on `updatedAt`, which `updateJobs` sets on every claim (`utilities/updateJob.js`), so a fresh claim is never stalled.
  - `config.jobs.enabled` is Payload's own gate for creating `payload-jobs` (`config/sanitize.js:278-280`), set once any task, `schedulePublish` included, is registered. Both ports check it first.
  - `summariseRun` reads 3.90.2's `RunJobsResult`: `jobStatus`, `remainingJobsFromQueried`, `noJobsRemaining`.
- **The jobs route.**
  - Auth comes before busy, and busy before anything is loaded. The limit can be lowered and never raised.
  - A throw is logged through `describeError` (the test proves `hunter2` never reaches the log) and answered with a plain 500.
  - A module that fails to load is also a plain 500.
  - The single-flight has no await between its check and its set.
- **The revalidate route.**
  - The profile comes from `tagExpiry` alone; a `profile` or `expire` key in the body is ignored (the test, and live, where availability expired at once).
  - `invalidate()` dedupes the tags and re-checks each one.
  - An `after()` that throws is answered 500.
  - `postTags` to the route to `invalidate` is exercised end to end with 259 tags in two bodies (`revalidate.test.ts:180-194`).
- **The fence.**
  - `grep` finds a value import of `@engine/cms` only in `health/payload-ports.ts:21-22` and `cron/jobs/payload-queue.ts:11`.
  - A static import of a `payload-*` module appears only in its own test.
  - `route.test.ts` and `cron.test.ts` `vi.mock` the ports module to throw, so a static import would fail the file.
  - The routes are factories taking the loader (§15 condition 2).
  - The package's `"./*": "./src/*/route.ts"` export makes a `payload-*` module unreachable as a subpath.
- **The placeholder move (4.6.d).**
  - `unbuilt/` and `shared/respond.ts` land as C13 v1.3 names them.
  - No reference to `legacy/unbuilt`, `legacy/respond`, `brandIcons` or `rootFileAsset` remains anywhere in `engine/`, `docs/` or `.github/`.
  - The placeholder's POST reads no body, and its GET reads the request (all `ƒ`).
- **The shell (4.6.e).** `load-shell.ts` takes both names from `BRAND_ROOT_ASSETS` and `versionedBrandAssetUrl()`, which gives `null` when a file is missing. `generateMetadata` reads `shell.assets` alone.
- **Files and dependencies.** Every file is under 300 lines, the largest being `revalidate.test.ts` at 195. http declares `@engine/cms` and `@engine/cache` only, and never `payload`. The lockfile change is the two `link:` entries.
