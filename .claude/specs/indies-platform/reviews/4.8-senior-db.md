## What I verified against installed code

- **The after-commit ordering — the named concern — holds in both write paths.** `invalidate()`'s premise is that Payload runs its hooks before it commits. Confirmed in the installed Payload 3.90.2: `collections/operations/create.js` — `afterOperation` at :403, `commitTransaction(req)` at :421; `update.js` — `afterOperation` at :336, `commitTransaction` at :347. A `revalidateTag` fired in a hook would therefore cache a pre-commit row as fresh — which is why `invalidate()` never revalidates on the spot, and the implementation honours it: with no collector it defers the whole batch into `after()` (runs once the response has been sent, i.e. after commit); with a collector it only collects, and the caller's `flush()` posts after its operation has returned. `invalidate.test.ts` proves the ordering with Next's **own machinery** — a real `AfterContext`, the real `workAsyncStorage`/`workUnitAsyncStorage` stores and a recording incremental cache — and asserts `committed: true` on every expired batch: nothing is expired while the request is open.
- **`after()` + `revalidateTag()` is proven, not assumed.** The test drives Next's installed `AfterContext` end to end and records the expiry batches: editorial tags expire with the `'max'` profile's duration, availability/price with `{ expire: 0 }`, grouped per profile exactly as `tagExpiry()` says — and the profiles are taken from the tag's kind, never a caller's argument (asserted both ways). The production-build proof remains 4.6.f's, as planned.
- **A forgotten collector fails loudly.** Outside a request with no collector — `undefined`, `null`, `{}` and even an empty tag list — `invalidate()` throws `after()`'s own error (`/outside a request scope/`): a failed save, never a silently stale page. A context whose collector key holds a foreign object throws `is not an invalidation collector`. A tag no builder makes throws before anything is scheduled, and nothing expires (`req.expired === []`).
- **The one-instance rule and its failure path.** `cms()` = `getPayload({ config })`; Next's `getPayload` caches per process, and a failed init clears the cached promise, so the next call retries — asserted by the sentinel-refusal test (`cms()` rejects `/cannot connect to Postgres/`, the listener counted ≥ 1 accept, and the import itself counted **0** connections). `cmsPool()`'s cast throws `payload.db.pool.connect is not a function` on an unconnected instance or a foreign adapter — asserted against four shapes — and against the real adapter answers READ COMMITTED via `databaseProbe()`.
- **The leaf really is a leaf.** Sources import only `next/cache`, `next/server` and their own relative modules — not even C1's types in source (they live in devDependencies and the tests); `next` pinned `16.3.6` as devDependency behind the peer range `>=16.3.3 <17`, and `leaf.test.ts` asserts the lockfile still resolves **one** `next`. The C13 restatement (`REVALIDATE_ROUTE`) is held against the manifest source by a test — I verified today's values are equal: `maxTags: 256`, `maxBodyBytes: 64 * 1024`, path `/api/x/revalidate`, owner WEB, POST, in `engine/packages/http/src/manifest.ts:124,154`.
- **The post path is safe to retry.** `revalidateBodies()`'s byte accounting is right (I hand-checked `{"tags":["a","b"]}`: frame 11 + 3 + 1 + 3 = 18); bodies cap at 256 tags / 64 KB; `postTags()` sends `redirect: 'error'` so the bearer cannot follow a redirect, times out at 10 s, accepts only 204, and tracks partial acceptance — `RevalidatePostError.accepted` — so a retry posts only what the route had not accepted; the collector's flush is serialised through a promise chain, and its generation stamps keep a tag re-kept while a flush is in flight for the *next* flush.

## Findings

1. **note** — `invalidate.test.ts` imports Next internals (`node-environment-baseline.js`, `work-async-storage.external.js`, `AfterContext`) to stage the request. This is a test's view of Next's internals, declared as such in its header; `invalidate()` itself probes nothing, which is the clause 4.8.c actually specifies. No action.
2. **note** — `collector.ts` documents (and its stage-drop implements) the edge where a unit that commits twice and then throws drops the first commit's tags: the fix is "make it two operations". The doc comment carries the rule where the next author will meet it. No action now; the outbox lane (18.2) should read it.
3. **note** — `revalidateTargetFrom()` defaults to `process.env`: in a jobs worker, `SITE_URL` and `REVALIDATE_SECRET` must be in that process's environment. DEPLOYMENT.md §8 owns the table; the throw names exactly what is missing, never a value. Covered when 5.x checks the crontab.

## Verdict

Nothing blocks the merge. The route it posts to (`/api/x/revalidate`) is 4.6.f's, whose Check includes the production-build proof of `after()`.
