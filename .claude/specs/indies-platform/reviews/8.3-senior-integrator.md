# 8.3 Media and masters: senior-integrator review

Branch `worktree-agent-a8ce4bf9698372e36` @ b8f5181 (base 39a1c50). Reviewed `git diff 39a1c50 b8f5181`. I changed no branch code. Each probe was a temporary `*.storage.db.test.ts` next to `test-stack.ts`, deleted after its run. `git status` is clean afterwards.

## Verdict: **sign off with should-fix**

I found no way for the public to reach an original or a master. That covers the bucket, Payload's file route, `url`/`thumbnailURL`, `disablePayloadAccessControl` (never set) and GraphQL (`graphQL: { disable: true }`). The presign is bound to one key, one length and one SHA-256, and the storage refuses other bytes. The policies are least-privilege enough for local, and I proved them against MinIO.

Four should-fix items stand out:

1. The 90 MiB media limit cannot be reached over REST. Payload's default 20 MiB cap applies first.
2. Anonymous `GET /api/media` lists every image, unpublished ones included, with `assetId` and `filename`.
3. A request can rewrite `media.provenance`.
4. Outlet and brand attribution on `masters` is loose.

None of these is unsafe to merge: each fails closed or is latent until 15.1. Fix 1 and 3 before the admin is used for real, and 2 before 15.1 writes derivatives.

## Findings

### 1. should-fix: the 90 MiB media limit is unreachable over REST and the admin; the real cap is Payload's default of 20 MiB

- `engine/packages/cms/src/payload.config.ts:86-125` has no `upload` key. Payload 3.90's multipart defaults therefore apply (`payload/dist/uploads/fetchAPI-multipart/index.js:5-27`): `fileSize: 20 MiB`, `requestSizeLimit: 50 MiB`, `abortOnLimit`, `useTempFiles: false`.
- `refuseOversizedUpload` (`collections/media/hooks.ts:27-36`) only ever fires on the Local API. The branch's 413 test uses the Local API (`media.storage.db.test.ts:149-161`), so it never exercised this path.
- **Reproduction** (probe, REST multipart as a cataloguer):
  - 19 MiB returned `201`.
  - 21 MiB returned `413 {"message":"File size limit has been reached"}`.
  - 60 MiB returned `413 {"message":"Multipart request size limit has been reached"}`.
- **Impact:** an exported 25–80 MB TIFF of a large sheet is refused, without the hook's helpful words. The limit claimed in 8.3.d is not the one enforced.
- **Fix** (in SCH's `payload.config.ts`, so a cross-lane follow-up or a grant):
  - Set `upload: { limits: { fileSize: MEDIA_UPLOAD_MAX_BYTES }, requestSizeLimit: MEDIA_UPLOAD_MAX_BYTES + 4 MiB, useTempFiles: true, tempFileDir: <os tmp> }`.
  - With `useTempFiles: true`, a 90 MiB body is streamed to disk instead of held in memory per request. `sha256OfUpload` already handles `tempFilePath`.
  - Keep the hook as the backstop for the Local API.
  - Add a REST test at `MEDIA_UPLOAD_MAX_BYTES + 1` (expect 413) and at about 30 MiB (expect 201).

### 2. should-fix: anonymous REST lists every `media` record, unpublished images included, with `assetId`, `filename`, `prefix`, `url` and caption

- `collections/media/access.ts:22-23`: `readMedia` returns `true` for anyone unless `isReadingStaticFile`.
- **Reproduction:** anonymous `GET /api/media?depth=0&limit=1` returned `200` with `{"caption":"unpublished work","assetId":"7c83f824…","prefix":"uploads","filename":"IMG_GPS_camera.jpg","url":"http://localhost:4199/api/media/file/IMG_GPS_camera.jpg?prefix=uploads",…}`.
- **Impact:**
  - It enumerates every image, including those of works not yet published (consignments, pre-announcements), with their alt text and captions. This goes against AGENTS.md: "Public reads are published-only and projected".
  - Once 15.1 runs, `assetId` is the secret part of `derivatives/v1/<assetId>/<w>.<fmt>`, which is public. Any unpublished image becomes viewable.
  - Camera filenames leak.
  - The file itself stays 403, so this is not an Exif leak.
- **Fix:** public reads go through loaders on the Local API, so close REST to the public: `read: ({ req, isReadingStaticFile }) => isStaffUser(req.user) || (!isReadingStaticFile && req.payloadAPI === 'local')`. Alternatively, field-hide `filename`, `prefix`, `_objectKey`, `url` and `assetId` from non-staff on REST. Add a test: anonymous `GET /api/media` returns 403 or an empty list.
- **Ask ARC:** confirm that `media` read is "loaders only", then the sister API projects explicitly.

### 3. should-fix: `media.provenance` and `role`, and a master's `role`, `provenance` and `brand`, can be rewritten by any writer

- `collections/media/hooks.ts:101-130` checks role and provenance against the master only when `master` is set. Editorial and legacy media have none, so a `contributor` can PATCH `provenance: 'ai-generated'` to `'photograph'`. That drops the synthetic label everywhere: a trust and compliance problem.
- `collections/masters/hooks.ts:60-87` (`keepWhatIsFixed`) freezes `kind`, `checksum` and `storageKey` but not `role`, `provenance` or `brand`. CONTENT-MODEL §6 says these are "set once at intake". A changed master also never propagates to its media.
- **Reproduction:**
  1. `POST /api/media` with `provenance: 'ai-generated'` as a contributor.
  2. `PATCH /api/media/<id>` with `{ "provenance": "photograph" }`.
  3. It returns 200. Nothing in `hooks.ts` refuses it.
- **Fix:** treat provenance (and role) as immutable after create on any API but the Local one, or allow the change only to `admin`/`manager` with a reason. Apply the same to masters. Test it.

### 4. should-fix: brand and outlet attribution on `masters` is enforced only at presign time

- `upload-url.ts:104-109` refuses captures for an outlet. `POST /api/masters` does not, and `verifyInBucket` HEADs with the outlet key, which may `GetObject masters/*`.
- `fillFromKey` (`masters/hooks.ts:35-45`) stamps `brand` with the process's brand. The validators check `brand` against the key only for intake keys (`validators.ts:127-138`), never against `printFileKey`'s `<brand>` segment.
- **Reproduction** (probe, emporium storefront, `test-masters-outlet`, cataloguer):
  - `POST /api/masters {kind:'capture', storageKey:'masters/w-probe/<sha>.tif', …}` returned **201**: the outlet DB records an origin capture as its own.
  - `POST /api/masters {kind:'print-file', storageKey:'print-files/someone-else/d-1/<sha>.tif', …}` returned **201**, with `brand` = the process brand and not `someone-else`.
- **Fix:**
  - Refuse `kind: 'capture'` in `checkConsistency` when the active brand is an outlet. If an outlet ever needs to reference a master, it does so by key from the C12 snapshot, not by a record.
  - Require `print-files/<record.brand>/…` and `record.brand === activeBrand().slug` on create.
  - Freeze `brand` on update.
  - The intake import should also refuse a manifest whose `brand` is not served by the origin process, or document that it may.

### 5. should-fix (DevOps/ARC follow-up, not this lane's code): least privilege on the irreplaceable archive, and RustFS parity

- `policies/masters-origin.json:11-20` gives the origin web process `s3:DeleteObject` on all of `archive-masters/*`. A compromised web process can therefore erase the archive.
  - Only 15.4's filing step (deleting the intake copy after a verified copy) needs delete.
  - Fix: either move delete into a separate key used only by the filing job or CLI, or require bucket versioning and object lock (or retention) on `archive-masters` in DEPLOYMENT §2.
- `policies/masters-outlet.json:21-30`: the outlet may put and delete all of `print-files/*`, not only `print-files/<outlet-slug>/*`.
  - Today only the outlet writes print files, but the origin is allowed to as well (`upload-url.ts:83`), so their files would share a writable prefix.
  - Fix: scope it with a per-user `{{brand}}` placeholder in the plan.
- **RustFS:** the completion integrity of 8.3.b depends on two storage behaviours:
  - The storage verifies `x-amz-checksum-sha256` on a presigned PUT and refuses a mismatch with 400.
  - HEAD with `ChecksumMode=ENABLED` returns `ChecksumSHA256`.

  MinIO does both. If RustFS stores the header without verifying it, records would vouch for bytes they do not hold: fail-open. If it does not return the checksum, every create is refused: fail-closed. `apply.mjs` also assumes RustFS answers `mc anonymous set-json` and `mc admin policy/user`. 41.2 must re-run `policies.minio.test.mjs` and the "tampered" PUT test (`masters.storage.db.test.ts`, "refuses a record … with other bytes") against RustFS before relying on it, and ship a `plans/staging.json` using `--secrets env`. Production is derivable from the plan files, but it is unproven on RustFS.

### 6. nit: `test-stack.ts` is test support under `src/`

`collections/media/test-stack.ts` imports `pg` through `createRequire`, mutates `process.env`, and falls back to `minioadmin`. Only the two `*.storage.db.test.ts` import it, and no package export reaches it, so it cannot get into an app bundle today. Rename it to `test-stack.test-support.ts`, or move it under a `__tests__/` folder that `check:client-safe` and the tsconfig `include` treat as test-only, so a future barrel cannot pull it in.

### 7. nit: `plans/local.json` names `ig-…` and `oei-…` buckets and users under `engine/`

The brand-literal lint passes, and DEPLOYMENT §2 uses these names. Still, it is a per-brand fact living in engine data. Consider moving the plan beside the dev compose file (repo root or `tooling/`), and keep `engine/` holding only the documents and the applier.

### 8. nit: TIFF covers TIFF-based RAW

`image/tiff` in `MEDIA_UPLOAD_MIME_TYPES` (`storage/limits.ts:23-29`) admits DNG and many RAW containers, because file-type sniffs them as TIFF. Payload does not decode them now, but 15.1 will. Either make 15.1 refuse a non-baseline TIFF, or drop TIFF from media: a processed web image is JPEG, PNG, WebP or AVIF, and TIFF belongs to masters.

### 9. nit: `masterKey(workUid=…)` accepts `workUid: 'intake'`

That produces `masters/intake/<sha>.<ext>`, which sits under `INTAKE_MASTERS_PREFIX` but has no brand or batch, so `isIntakeKey()` reports true for it. Reserve `intake` in `parseUploadRequest` (`upload-url.ts:57-75`). The `work` relation is also never cross-checked against the key's uid. That cross-check is 15.4's to add when filing.

## Recommendations on the Found items for ARC

### (2) Synthetic label: store it in the alt, or add it at render? **Add it at render.**

- Keep the CMS `alt` as the description only. The view-model builder (C2) composes `alt = t('image.syntheticAlt.<label>') + ': ' + alt` from `provenance` for every synthetic image. It uses the same `opensWithLabel` guard so a legacy alt that already opens with the label is not labelled twice.
- **Why:**
  - The label is a provenance invariant that must hold "wherever it appears", not editorial text. Stored in the alt, a cataloguer improving it can delete it.
  - Lexicon wording and locale changes then propagate without rewriting records.
  - `altBaseline()` no longer needs lexicon words passed into a CMS write, so the CMS stays lexicon-free.
  - Finding 3 (frozen provenance) then makes the label un-removable.
- Keep `altBaseline()` for the description part only, and add a save-time warning when a stored alt begins with a label's words. Adopting this means rewording C9 and CONTENT-MODEL §6 ("at the start of its alt text" becomes "at the start of its rendered alt text").

### (3) Where the outlet's full-resolution IIIF pyramid lives. **In each brand's own media bucket, under a private `iiif-full/` prefix, for both brands.**

- C9 `iiifFullKey()` currently puts it in `MASTERS_BUCKET`, where the outlet key may write only `print-files/`.
- **Why the media bucket:**
  - The pyramid is derived from the `media` upload, not from the master. That upload already lives privately under `uploads/` in the same bucket at full resolution, so this adds no new exposure class.
  - The brand's media key already writes there.
  - The masters bucket stays "origin captures plus print files" exactly as DEPLOYMENT §2 states.
  - The staff route `MEDIA_ROUTES.fullTiles` streams with the brand's own key.
- **Why not the alternative:** widening `masters-outlet` with `iiif-full/<outlet>/*` puts derived and rebuildable data in the irreplaceable archive bucket, and weakens the one-line rule "the outlet writes only print-files/".
- **Required:**
  - C9 rewords `iiifFullKey` ("brand media bucket, private") and can drop the `brand` segment.
  - The public policy keeps `iiif/*` with its slash, since `iiif-full/` must not match.
  - Add a MinIO test: anonymous `GET iiif-full/<id>/info.json` returns 403. `isPublicMediaKey('iiif-full/…')` is already false.
  - The 15.2 Check's "private prefix" follows.
