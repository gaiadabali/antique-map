# 4.1 review — senior-be (`@engine/http`: brand-assets, health, cron, legacy)

Reviewed `feat/p4-web` at 8b78826 (one commit on e4da692), `engine/packages/http/src/{brand-assets,health,cron,legacy}/**` and the apps' mounts, `boot.ts` and `instrumentation.ts`. `vitest run` over the four suites: 4 files, 59 tests green (the http package as a whole: 9 files, 90). A fresh gallery `next build` with no `BRAND` or `DATABASE_URL` passed and lists every `/api/**` and `/brand-assets/[...path]` route as `ƒ`. Nothing ran at build. A `next start` on :4210 (`BRAND=test`, a scratch brand root with junctions planted) was probed with `curl --path-as-is`. Raw `..` and `%2e%2e` are normalised by Next before routing, so they reach the designed 404 page, never the handler. `%252e%252e`, `..%2f`, `..%5c`, `%5c..%5c`, `fonts%2f..%2f..%2f`, `C:%5c…`, `%00`, a trailing dot or space, `;x.png`, ADS (`::$DATA`), `CON.svg`/`NUL.png`, 8.3 names, fullwidth dots and a junction out of the folder all get a plain `no-store` 404. `//` gets Next's 308. HEAD and OPTIONS are automatic, and POST gets a 405. Cron: 401 without or with the wrong bearer, then 503 not-wired or a 404 stub, and GET gets a 405. Health answers 503 `not-wired`, `no-store`, and leaks no finding text. The worktree was left clean. Note: the senior-fe reviewer rebuilt `.next` in the same worktree while I was probing, and the first run's page-route 500s ("client reference manifest does not exist") came from that rebuild. They were re-probed clean on the rebuilt output.

**Verdict: sign off with should-fix.** I found no traversal, no leak and no auth bypass. #2 must land before 5.1. #1 and #6 are cheap and belong in this branch or its fix pass. #3–#5 are requirements on the 4.6 wiring, recorded now because the ports decide them.

1. **should-fix** — `health/health.ts:53-54, :78-84`: `settle()` swallows the database port's error, and `boot(null)` then runs without a probe. So a 503 `database: error` leaves **no cause in any log**: the process log gets a boot report whose `problems` are `[]`. Once wired, that is the deploy's first `getPayload()`, so a failed migration or a refused connection is invisible to the operator. Evidence: `health.test.ts:71-86` passes with the ECONNREFUSED text logged nowhere. Its `log` is `() => {}`, and a spy would receive a clean report. Fix: when the database port throws, hand `runBootCheck` a probe that rethrows that error. Its `checkDatabase()` already turns it into a finding with credentials redacted, so it reaches `formatBootReport` and the log, never the body. Test that the log receives the redacted cause and the body still does not.
2. **should-fix (before 5.1)** — `apps/*/src/app/api/x/robots/route.ts` → `legacy/unbuilt/route.ts:13-17`: `/robots.txt` answers 404, which crawlers read as "allow everything". 5.1 needs only 2.3 and 4.1, and it puts `ig.gaiada.com` and `oei.gaiada.com` on the public internet serving fixture shells under the brands' names. SEO's per-environment robots comes phases later. Evidence: `curl -i :4210/robots.txt` → `404 text/plain; no-store`. Fix: a fail-closed placeholder for this one mount, `200 text/plain` `User-agent: *` / `Disallow: /`, in WEB's paths (e.g. `@engine/http/legacy/unbuilt/robots`), until SEO lands. Or 4.3.b's placeholder policy says so. Everything else about the shared placeholder is sound (see item 4 below).
3. **should-fix (4.6)** — `health.ts:70` gates the status on `queue`, and the release flow rolls back on a failed health check (DEPLOYMENT §3). DEPLOYMENT §7 makes queue lag an Alloy **alert**, not a deploy gate. A stuck derivative job would roll back every release, including the one that fixes it. The proven wiring (`scratchpad/wired/payload-ports.ts:28-34`) also counts every job with no `completedAt`. That includes jobs with `hasError: true` and jobs whose `waitUntil` is in the future, and Payload's own `runJobs` never picks either (`payload/dist/queues/operations/runJobs/index.js:24-52`). One permanently failed job, or tomorrow's scheduled digest, fails health forever. Fix: report the queue check but leave it out of the status code (or answer `degraded` with a 200). Mirror `runJobs`' `where` for lag, and treat `processing: true` older than N minutes as the real stall.
4. **should-fix (4.6)** — `cron/jobs/route.ts:24` via the wired `payload.jobs.run({ limit })`: Payload runs only the `default` queue unless told otherwise (`localAPI.d.ts`, `run.queue` "@default jobs from the `default` queue", `allQueues` false). A task registered on another queue would never run. Pass `allQueues: true`. Also, a run longer than a minute overlaps the next crontab tick. `runJobs` claims with `updateJobs({ processing: true }, disableTransaction: true, limit)`, so do not rely on it. Add an in-process single-flight (a module-level promise, answering 409 or 202 `busy`), which is exact while there is one web process per brand. Wrap `queue()` so a throw becomes a logged, plain 500, not Next's.
5. **should-fix (4.6)** — once wired, each unauthenticated `GET /api/health` costs a pool checkout plus 2–3 round trips on the pool the page loaders use. `payloadDatabase()` calls `probe()` (`payload-ports.ts:19`), `runBootCheck`'s `checkDatabase` calls it again, and the queue query adds another. A burst drains the pool. Fix: single-flight plus a memo of about 5 s on `checkHealth`, and probe once. Today it costs nothing: 13.3 ms/req sequential against 13.7 ms for a brand asset, 300 requests each.
6. **should-fix** — `brand-assets/resolve.ts:33-47` applies the dotfile rule and the extension rule to the **URL** only, never to the real path. A link *inside* the folder therefore serves a dotfile, or a file of another type, under a listed type. The header at `:3-6` says "a dotfile … is no asset". Evidence: a junction `assets/pub → assets/.private` (junctions need no privilege on Windows) makes `GET /brand-assets/pub/p.png` answer `200 image/png` with body `PRIVATE`, while `/brand-assets/.private/p.png` answers 404. On Linux a file symlink `env.png → .env` serves `.env` as `image/png`. It needs a link committed to a brand folder, but the fix is two lines. Re-check `relative(root, file)`: every segment passes `SEGMENT`, and `brandAssetExtension(real) === extension`. Add the in-folder link to the test table. Hard links cannot be told apart and are out of scope, since the brand folder is trusted content.
7. **nit** — `resolve.ts:41` + `version.ts:26-38`: on a case-insensitive filesystem (Windows, macOS workstations), `realpathSync` keeps the request's spelling. So `/brand-assets/LOGO.SVG` answers 200, and each case variant is a **separate cache entry holding the whole file**. Evidence: `readAsset(resolve('logo.svg')).bytes === readAsset(resolve('LoGo.SvG')).bytes` → `false`. `realpathSync.native` gives `\logo.svg`. Enumerating variants grows memory without bound. Helios is Linux, hence a nit. Fix: `realpathSync.native`, or key the cache by `dev:ino`.
8. **nit** — `version.ts:34`, `serve.ts:59`: there is no size cap. The whole file is read, pinned for the process's life, and `new Uint8Array(content.bytes)` **copies it on every 200**. A master scan dropped into `assets/` by mistake costs its size per concurrent request. Fix: cap it (e.g. 5 MB → 404 plus a log line; `validateBrandConfigs()` can refuse it earlier), and build the `ArrayBuffer`-backed view once at read time.
9. **nit** — `resolve.ts:41-42` → `version.ts:30-34`: the file is checked and then reopened by name (TOCTOU). Exploiting it needs write access to the brand folder. Fix: `openSync` once, `fstatSync`, read from the fd. Also, `serve.ts:43` lets a `readAsset` throw (file removed, EACCES) become Next's 500, while the rest of the route "never throws". Catch it and answer 404.
10. **nit** — SVG CSP `default-src 'none'` (`serve.ts:53`) is right. As an `<img>`, Chromium ignores it: a test SVG whose `<style>` turns a blue rect red rendered red. Opened directly, it rendered blue, script and style both blocked. Illustrator-exported logos carry `<style>`, so consider GitHub's user-content policy, `default-src 'none'; style-src 'unsafe-inline'; sandbox`, which keeps them readable when opened and gives them an opaque origin. Firefox was not available here; 4.4.b's smoke should look.
11. **nit (HAR)** — `withPayload()` adds `Accept-CH`, `Critical-CH` and `Vary: Sec-CH-Prefers-Color-Scheme` to **every** response (`.next/routes-manifest.json`, source `/:path*`), including the `immutable` brand assets, their 304s and the API JSON. A shared cache splits each asset on that hint. Scope it to `/admin` if `withPayload` allows.
12. **nit (PLT/HAR)** — Next itself answers malformed percent-encoding under the paths the proxy does not see with a bare 500, and logs nothing: `/brand-assets/%E0%A4%A.svg`, `/brand-assets/%C0%AE%C0%AE/…` and `/api/x/legacy/%E0%A4%A` → 500, while a page path → 404 through the proxy. Our code is never reached and nothing leaks, but a scanner can trip DEPLOYMENT §7's 5xx-rate alert. Note it where the alert is defined.
13. **nit** — the health body is public and carries `problems`/`warnings` counts (`warnings: 42` on :4210) and `environment`. That is acceptable, and §8 asks for `environment`. The counts are the only non-essential part; drop them if you like. `ports.ts:37` runs the boot check without the app's `supports`, which `boot.ts:14` passes, so the health route's re-check is not quite the one start ran. `ports.boot` and `ports.storage` are not settled, so a throw is Next's 500, contrary to `health.ts:77`'s claim.
14. **nit** — cron: the constant-time compare is sound. `timingSafeEqual` over two SHA-256 digests is 32 bytes against 32, so no length leaks, and it trims like the boot check's `read()`, whose ≥ 32-character rule covers `CRON_SECRET`. `?limit=` can lower the host's limit and never raise it. `1e1`/`0x10` parse, which is harmless. Two small points: the scheme compare is case-sensitive (`bearer` → 401, where RFC 9110 §11.1 is case-insensitive), which is fine for our crontab; and the jobs JSON answer lacks `nosniff`. Operationally, 5.1's crontab calling a not-wired `/api/x/cron/jobs` every minute puts 1,440 503s a day into the 5xx alert. Install that line with 4.6, not before.
15. **nit** — tests: `brand-assets.test.ts` has **30** cases, not 33 (4 types, 1 CSP, 13 refusals, 1 immutable, 2 unversioned, 4 × 304, 1 × 200, 4 URL). They test what they claim: each C1 type, `nosniff`, the SVG CSP, `no-store` 404s, immutable only at the current `v`, strong ETag, weak / list / `*` 304s, and minting that follows an in-place replace. Missing: #6's in-folder link, the 304's headers (`ETag`, `Cache-Control` present, no body), and the `route.ts` wrapper (no brand → 404). `health.test.ts` covers the ports' logic well but not #1's log content. The prerender guard (`route.ts:15-17`) is proven only by the build (`ƒ /api/health`), which is enough. `cron.test.ts` and `legacy.test.ts` match their claims.
16. **nit** — there are two identical `notFound()` helpers (`brand-assets/serve.ts:29`, `legacy/not-found.ts:2`). Keep one.

**The shared 404 placeholder (`legacy/unbuilt`, 34 mounts per app) is sound as a stopgap.** Its answers are `no-store`, `text/plain`, `nosniff` and carry no `Location`. The GET reads the request, so no static mount (`/api/x/robots`, `/api/x/revalidate`) is prerendered; the build lists all of them `ƒ`. The POST reads no body and changes nothing, so a cookie-authenticated or cross-origin write reaches nothing. Every method matches C13, and route parity is green. Robots is the exception (#2). A provider webhook pointed at staging before PAY lands would 404 and could be disabled by the provider, so nobody configures one until PAY ships. The name is misleading, since it is not a legacy handler. Route parity does not assert `handlerOf(path)`, so a lane can forget to repoint its mount. Both points are already on 4.3.b.

## Item 5: how `/api/health` and `/api/x/cron/jobs` reach Payload

**Recommendation: `@engine/http` depends on `@engine/cms`; do not use app-injected ports.** Add a `payload` dependency to http only if SCH declines the getter in condition (a).

App injection does not work under the repo's own rules:
- Boundary 1 (`eslint.config.mjs:140-147`) forbids `payload` and `@engine/cms` in `src/app/api/health/route.ts` and in `src/instrumentation.ts`. Only `src/app/(payload)/**` is exempt.
- Moving the mount into `(payload)` changes the file route parity demands (`route-parity/app-mounts.mjs:22`, `src/app/api/health/route.ts`). It also breaks the one-line-mount rule.
- Every DB-backed handler still to come would need the same injection, twice: commerce (DOM's `reserve()` needs the pool), forms, auth, privacy, sister, media, search.
- The layering already puts Payload behind packages. Loaders are "Payload Local API → view models" (ARCHITECTURE §4), and http is the server composition layer at the same altitude. Boundary 1 exists to keep Payload *out of* apps, so injecting it from the apps defeats it.

Conditions, all for 4.3.a to record and 4.6 to land:
- **(a)** SCH exports the instance from cms, e.g. `@engine/cms/instance` with `cms() = getPayload({ config })`, beside the existing `@engine/cms/db/probe`. The one config import and the `payload` pin then stay in cms, and http declares only `"@engine/cms": "workspace:*"`. If `payload` is declared in http after all, it must be exactly cms's `3.90.2`. A second copy would split `getPayload`'s global cache: two instances, two pools, and migrations raced.
- **(b)** Load Payload **lazily**: `const { payloadPorts } = await import('./payload-ports')` inside `GET`/`POST`, after the request is read. Top-level imports would evaluate the Payload config during `next build`'s page-data collection and inside route parity's TS runner, which `import()`s every mount (`app-mounts.mjs:37`). They would also make `health.test.ts:112` (`GET(...)`) reach for a database. Keep the pure ports (`checkHealth`, `perRunLimit`) importable without cms.
- **(c)** Fence it with an ESLint override (HAR): no `payload`/`@engine/cms` import under `http/src/{proxy,manifest,brand-assets,legacy}/**` or `http/src/manifest.ts`. The proxy "never touches the database". The manifest is read by route parity and by server components (`not-found.tsx`, the item page). `brand-assets` is imported by the shell (`shell/load-shell.ts:10`).
- **(d)** No cycle: cms never imports `@engine/http` (an ESLint rule on `engine/packages/cms/**`). `invalidate(tags)`, which cms hooks call (CONVENTIONS §12), therefore lives in loaders or a leaf package, never in http.
- **(e)** Client-safe: nothing new. The gate already refuses `payload`, `@payloadcms/*` and `@engine/cms` wherever a `'use client'` module transitively reaches them (`tooling/client-safe/rules.mjs:24-27`). No http subpath was ever client-safe anyway: `brand-assets` reaches `node:fs` and `@engine/config/loader`. Keep `manifest` type-import-only, as it is.
- **(f)** The build never touches a database: (b), plus the request read that already comes first. 4.6.c's check should build with `DATABASE_URL` unset *and* sockets refused, as 3.1.e's proxy probe did.

The 4.6 files are then: `engine/packages/http/package.json` (outside every lane's Owns; ARC or HAR grants it), `http/src/health/{route,payload-ports}.ts`, `http/src/cron/jobs/route.ts`, and SCH's `cms/src/instance.ts` with its `exports` entry.
