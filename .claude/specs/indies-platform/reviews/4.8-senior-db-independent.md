## Findings

1. **S1 should-fix (before 8.2.e, 9.1.e, 18.2.d, seeds and MIG).** `cache/src/collector.ts:120-128`, and the spec that asks for it: TASKS.md 4.8.c ("dropping it on a throw") and ARCHITECTURE.md §9 ("a throw, a rolled-back save, drops it").

   **The problem.** "Kept when `write` resolves, dropped when it throws" is exact only when the operation is exactly one transaction and that transaction is Payload's own. Rows B and C show two reachable paths where a write **committed** and its tag was **dropped**, with no error anywhere:
   - `disableTransaction: true`, which bulk importers reach for;
   - a hook's nested write in its own transaction, before a later hook throws.

   The documented third path is "a unit that commits twice and then throws".

   The two modes also disagree. The in-request mode schedules `after()` whether or not the write rolls back, and that is harmless: expiring a tag whose content did not change costs one recompute. A dropped tag on committed content costs a stale page, and under `'max'` there is no backstop until the next edit.

   **Fix.**
   - Keep a thrown operation's tags, then rethrow.
   - Change the two sentences in 4.8.c and §9. This is ARC's text to edit, and SCH's code.
   - Make the class comment say "over-invalidation on failure is by design".
   - Replace `collector.test.ts:275-301` with the kept-on-throw cases, plus B and C as db tests (T1).
   - Keep the "adds after close throw" rule.

2. **S2 should-fix (same timing).** `collector.ts:16-20` and `:73`. **Two misuses that only a written rule prevents.**

   *(a) A caller-supplied `req`.* Row D1: with a live transaction on `req`, Payload's `initTransaction` returns `false`, and the operation resolves **before** the commit. The tags are kept for a write that may still roll back. That is the harmless direction, but it is not "after commit".

   *(b) The stage outlives its operation on the `req`.* Row D2: `createLocalReq` assigns `req.context = { ...req.context, ...context }` (`payload/dist/utilities/createLocalReq.js:4-18, :86`), so the closed stage stays on the `req`, and the next write through that `req` fails.

   In a job this spreads. `runJobs` hands each job `isolateObjectProperty(req, 'transactionID')`. That proxy's `set` trap writes every other key to the **shared** run-level `req` (`isolateObjectProperty.js`, `set`). So a task that passes `req` plus an operation's context poisons `context` for every later job in the run.

   **Fix.**
   - State in the class comment and in 18.2.d: "never pass `req` to a Local API call inside `operation()`; its `context` is the operation's alone".
   - With S1 done, give jobs a batch-level context, `batch.context()`, which keeps every tag and has no stage to close. A task passes it (with `req`), and the runner flushes it after the run.
   - Without that, the DEPLOYMENT §2 "escape hatch" (a `payload jobs:run` pm2 app) cannot run at all. Every hooked write there throws `after()`'s error, including Payload's own `schedulePublish` task.
   - The cron route is in-request, so it is fine as it is.

3. **S3 should-fix (with or before 4.6.a).** `cms/src/db/adapter.ts:57`, `db/probe.ts:15-27`, and 4.6.a's text. **The health probe can wait forever, and the pool is one smaller than it looks.**

   Row G shows three things:
   - The pool has `connectionTimeoutMillis: undefined`, pg's "wait forever". Under exhaustion, `databaseProbe()` waits with no bound: 3 s and still waiting.
   - There is no `query_timeout` either, so a black-holed TCP connection hangs the probe on its query while it holds a client.
   - Payload's `connectWithReconnect` (`db-postgres/dist/connect.js:4-8`) takes the pool's first client and **never releases it**. That is the one checked-out client with zero sessions in every count, so at most 9 clients serve work.

   Combine these with 4.6.a's "single-flight memo". If a probe hangs, every health check awaits it and the deploy's health check times out. If the memo is dropped on timeout, each new probe strands another client until the pool is gone.

   **Fix.**
   - Pass `pool: { connectionString, connectionTimeoutMillis: 5_000 }` in `buildDatabaseAdapter`, and a `query_timeout` on the probe's query.
   - In `databaseProbe`, call `client.release(error)` on failure, so a broken client is destroyed rather than pooled.
   - In 4.6.a: bound the probe (≈2–3 s → `database: down`, 503), and never start a probe while one is still pending.
   - `databaseProbe(cmsPool(payload))` itself does return its client (G).

4. **S4 should-fix (with or before 4.6.c).** `db/adapter.ts:56-62`. **Payload creates a database it cannot find.**

   `connect.js` catches `database … does not exist` and, unless `disableCreateDatabase` is set, runs `CREATE DATABASE` and reconnects (row "createdb"). A mistyped `DATABASE_URL` then boots on an empty database, and the probe still answers READ COMMITTED. So 4.6's `/api/health` would be green. With `RUN_MIGRATIONS=1`, it would migrate the empty database and serve an empty shop.

   On Helios this needs `CREATEDB` on the brand role. In CI and on workstations it is the superuser, and there it succeeds.

   **Fix.**
   - `disableCreateDatabase: true` in `postgresAdapter({...})`. `db:fresh` already creates the databases itself.
   - 5.1.a provisions `ig` and `oei` as `NOCREATEDB`.
   - Ideally, 4.6's database check also asserts that `payload_migrations` has a row.

5. **S5 should-fix (before the first out-of-request flush).** `cache/src/post.ts:27-51` (Found 1). **Post on loopback, not through Cloudflare.**

   `SITE_URL` is `https://<domain>`, so a worker on Helios would send the bearer through Cloudflare and nginx and back into the box. That path has four problems:
   - The secret is exposed to a third hop.
   - It depends on DNS and Cloudflare for an internal call.
   - Bot Fight Mode or WAF rules can answer an `undici` POST with a 403 or a challenge. That fails loud, but invalidation is then broken until someone notices.
   - A mis-set `SITE_URL` posts to another environment.

   Loopback is safe here, for four reasons:
   - The proxy does not run on `/api/`: its matcher is `/((?!api/|_next/|brand-assets/).*)`. So the loopback-literal rewrite hang (DEPLOYMENT §3) cannot happen on this route.
   - The web process listens on `127.0.0.1` alone (`HOSTNAME=localhost` with `--dns-result-order=ipv4first`).
   - The route authenticates by bearer, not by client address.
   - `redirect: 'error'` still holds.

   **Fix.**
   - A dedicated `REVALIDATE_ORIGIN`, read by `revalidateTargetFrom()` in preference to `SITE_URL`.
   - On a host it is `http://127.0.0.1:<PORT>`, the IP literal and not `localhost`: a worker's Node without `ipv4first` would resolve `::1` and be refused.
   - Add it to DEPLOYMENT §8 and to 5.1.a's `shared/.env` skeleton.
   - A tool that runs off-box posts to the public origin only with a Cloudflare skip rule for `/api/x/revalidate`.
   - Keep the `SITE_URL` fallback for local work.

6. **S6 should-fix (SCH follow-up; a Payload bug, not 4.8's).** `@payloadcms/drizzle/dist/transactions/beginTransaction.js` (`.catch(transactionFailed)` on an already-settled promise) and `commitTransaction.js`. **A `COMMIT` that fails is reported as success.**

   Row F: the transaction rolled back at `COMMIT`, yet `payload.create` resolved with the document. For the cache this is the harmless direction (a tag kept for nothing). For the data it is not. The engine already relies on a `COMMIT`-time refusal: the `users_roles_keep_an_admin` deferred constraint trigger (initial migration, 3.2 B1). When that backstop fires through Payload, the admin sees "saved" and nothing changed. `admins.db.test.ts:123-160` proves the trigger only through raw SQL, where `COMMIT` does reject.

   **Fix.**
   - In `withMigrationLock`'s `init` wrapper (`db/adapter.ts:87`), wrap `beginTransaction` so that it records the rejection of drizzle's `transaction()` per session, and wrap `commitTransaction` to rethrow it after `session.resolve()`.
   - Alternatively, carry a `pnpm patch` and file it upstream.
   - Add a db test: a Payload write whose `COMMIT` violates a deferred constraint rejects.
   - Any future `DEFERRABLE` constraint or `SERIALIZABLE` transaction depends on this.

7. **N1 nit (Found 2).** `db-postgres/dist/connect.js:95-97`. Confirmed: each failed connect rejects the adapter's `initializing` with no reason, and nothing awaits it.
   - Under `server.js`, Next's listener logs `unhandledRejection: undefined` once per attempt and keeps running (`next/dist/server/node-environment-extensions/process-error-handlers.js:75-99`). So 4.6's `/api/health` sees a clean rejection from `cms()`, answers 503, and leaves a reason-less log line per retry.
   - In a bare Node CLI (a seed, an import, `payload jobs:run`), Node's default `--unhandled-rejections=throw` kills the process before the caller's `catch` can retry.

   **Fix:** in the same `init` wrapper, `void adapter.initializing?.catch(() => undefined)`. That is the test's own patch at `instance.test.ts:87-94`, moved to where production gets it.

8. **N2 nit.** `@payloadcms/drizzle/dist/destroy.js` never ends the pool, so `payload.destroy()` leaves connections open. That includes the permanently held client from S3. My forced drop of the scratch database had to terminate one.

   **Fix:** tests (and 4.6.c's two-process race) end `payload.db.pool` explicitly after `destroy()`.

9. **N3 nit (docs for Server Action authors).** `invalidate.ts:37-39`. In a Server Action, `after()` runs after the action's response, and that response carries its own re-render. So the action never reads its own writes. `revalidate.js` already skips that for `'max'`, but an `{ expire: 0 }` tag would otherwise have been applied before that render.

   For purchase controls this is harmless, since availability is read live. A cached status in the action's own response can be one render stale.

   **Fix:** one sentence in §9.

10. **N4 nit (8.2.e, 9.1.e).** Drafts and autosave run `afterChange` on every autosave, through REST, in-request. A hook that expires `availability:` and `price:` on each one churns `{ expire: 0 }` entries with nothing public changed. `restoreVersion` and publish do change public content.
    - Hooks skip a save that is a draft before and after.
    - Hooks are registered **first** among `afterChange`. Neither mode acts before commit, so running first costs nothing, and it closes row E: a bulk update commits a document whose earlier hook threw, and that document's tags are never added. S1 cannot fix E, because the operation resolves.

11. **N5 nit (4.6.f and the outbox).**
    - A 204 from the route means "scheduled in `after()`", not "expired". No loss follows while the `'use cache'` handler is in-memory, since a crash loses the cache with the callbacks. Record it as an invariant: a persistent `cacheHandler` would need the route to expire before answering.
    - A 400, for example a tag kind the web process does not know yet while a deploy is half done, stops a flush at that body and keeps it and everything after it. The outbox must retry with backoff and alert, not loop.

12. **N6 nit (an invariant to record in §9).** If `readReplicas` is ever set, a regeneration right after an invalidation can read a replica that has not replayed the commit, and cache the old row as fresh: the very bug §9 prevents. Loaders read the primary.

13. **T1 should-fix (tests).** `cms/src/instance.test.ts:120-153` and `.github/workflows/e2e.yml:108-117`.

    **The database half never runs in CI.** It keys on `CMS_TEST_DATABASE_URL`, which no workflow sets, and CI's real-database step runs only `*.db.test` files on `CMS_TEST_POSTGRES_URL`.

    **Fix:** move it to `cms/src/instance.db.test.ts` on `CMS_TEST_POSTGRES_URL`, making, migrating and dropping its own database as `collections/users/admins.db.test.ts` does. The e2e step then picks it up with no workflow change. In the same file:
    - Commit the after-commit proof, which today exists nowhere in the repo: A1, A2, B and C, with S1's kept-on-throw expectations. `collector.test.ts` only simulates Payload with a `save()` stand-in.
    - The retry after a failed first connect, asserted rather than incidental: two `cms()` calls, both reaching the listener.
    - S4's refusal of a missing database, and S6's rejecting `COMMIT`, once each lands.

## Checked and correct

- **`cms()`.** Concurrent first calls share `cached.promise` (`payload/dist/index.js:543-636`), and a failure resets it so the next call retries, as Found 2 showed with 2 accepts.

  Latent: on a retry `getPayload` sets `disableOnInit: true`, because the cache entry already exists, so an `onInit` would be skipped. cms has none today.

- **Import opens nothing.** The sentinel test is sound: `DATABASE_URL`, `PGHOST` and `PGPORT` all point at the listener.

- **`cmsPool()`.** It returns the adapter's pool and throws for the four bad shapes.

- **Transactions in Payload's own operations.** `create`, `updateByID`, `update`, `delete`, `deleteByID` and `restoreVersion` all run their hooks, then `commitTransaction`, then `return`. `commitTransaction` awaits drizzle's `done`, the `COMMIT` round trip, so "resolved" means "the `COMMIT` completed" (only its failure is swallowed, S6).

- **Bulk operations.** With db-postgres, `bulkOperationsSingleTransaction` is unset. So a bulk update or delete is one outer transaction, its documents processed in parallel, and a failing document is reported in `errors` without rolling back the rest (E).

- **Jobs.** Each job gets an isolated `transactionID`, so every Local API call in a task is its own transaction, which is consistent with the rule "one `operation()` is one transaction".

- **`after()`.** `AfterContext` queues callbacks until `onClose`, then runs them under `withExecuteRevalidates` (`after-context.js`). `revalidateTag` throws outside a request, during `render` and in `'use cache'`, but inside `after()` the phase has become `'after'`, so it is legal there. `revalidatedAt` is taken when the callback calls it, after commit, so an entry computed from the pre-commit row counts as stale.

  Payload's REST save (the admin's save is a REST `fetch`) returns only after the operation has committed.

- **Bounds.**
  - Grammar: strict (no second spelling; kinds read with `Object.hasOwn`; ≤ 64 characters, under Next's 256).
  - `cacheTags` batches at 128.
  - Bodies: ≤ 256 tags and ≤ 64 KiB, with ASCII-exact byte accounting.
  - Only a 204 counts, and `redirect: 'error'`.
  - Partial acceptance: `forget(accepted)` from the front matches the order of the bodies.
  - Tags re-kept while a flush is in flight: the generation stamps keep them for the next flush.
  - Flushes are serialised.

  I found no silent loss in `post.ts` or the flush.

## Where this agrees and disagrees with `4.8-senior-db.md`

**Agree:**
- The ordering in Payload's own transaction (my A1 and A2 reproduce it).
- The `after()` proof on Next's own `AfterContext`.
- The leaf and its single `next`.
- Failing loud outside a request.
- The bounds and the in-flight logic.
- Its note 3, that the worker needs the variables.

**Disagree:**
- Its **note 2** treats "commits twice then throws" as a documented edge needing no action. Dropping on a throw loses committed writes' tags through `disableTransaction` and through nested own-transaction writes too (B, C). It contradicts the in-request mode's behaviour, and it blocks any jobs-worker integration (S1, S2).
- It says the retry after a failed init is "asserted by the sentinel-refusal test". That test calls `cms()` once; the retry is only incidental, in the next `describe`.
- It attributes `getPayload` to Next; it is Payload's.
- It ran the database half locally only, and does not say that CI never runs it (T1).
- It did not examine:
  - the pool's timeouts or the client Payload never releases (S3);
  - Payload creating a missing database (S4);
  - where a flush should post (S5, Found 1 left open);
  - the swallowed `COMMIT` (S6);
  - Found 2's consequence under Next versus a CLI (N1).
- Its verdict "sign off" should read **sign off with should-fix**. S3 and S4 bear on 4.6.
