I checked these claims against installed code (Next 16.3.6, Payload 3.90.2), and each one holds:
- **The loopback hang.** It is real, and no choice of origin in the proxy avoids it. `next-url.js:15` renames `127.x.x.x`, `[::1]` and `localhost` to `localhost`. `adapter.js:322-330` rewrites `x-middleware-rewrite` through `NextURL`. `resolve-routes.js:117` builds `initUrl` from `opts.hostname` (not the `Host` header). `:468` then compares origins, so an absolute rewrite always looks external.
- **A missing User-Agent is served the shell.** `streaming-metadata.js` has `if (userAgent && regex.test(userAgent))`, so an empty or missing UA streams metadata.
- **`_rsc` never reaches `x-public-search`.** `adapter.js:172` runs `stripInternalSearchParams`.
- **`cms()` gives one Payload per process.** `getPayload` caches on `global._payload`, keyed `'default'`, so the admin routes and a lazily bundled `payload-ports` chunk share one instance. A failed init clears `cached.promise` (`payload/dist/index.js:632`), so a health check after a failed first boot retries.
- **Ownership.** The C13 `owner` column matches every http folder in PARALLEL-TRACKS §1's rows today.
- **The 4.6.d move.** It edits nothing outside E10's Owns: DOM's and PAY's cron stubs import only `../auth`.
- **`@engine/http`'s `"./*": "./src/*/route.ts"` export** makes a `payload-*.ts` module unreachable as a package subpath. That is a good property, and it comes for free.

**Verdict: sign off with should-fix.** The §15 decision is the one I recommended, and conditions (a)–(f) of my 4.1 item 5 are all recorded. `cms()` and `cmsPool()` are right-sized as task 4.8, and C2 and C13 v1.3 are genuinely additive. Nothing in the branch is wrong enough to block the merge. #1–#4 must be fixed in the board edits **before they are applied**: two of them are ordering holes that would strand callers, and one is a transactional-integrity bug written into a task. #5 belongs to 4.3's fix round (4.3.f). #6–#9 are text changes to 5.3, 4.6.c and DEPLOYMENT §3.

1. **should-fix (before the edits land)**. E22/E23 (8.2.g), and ARCHITECTURE.md §15 condition 4. **`@engine/cache` is built after its callers, and no task builds `/api/x/revalidate`.**
   - **The ordering.** 8.2 (`needs: 8.1, 8.3`) builds the package. Its callers do not wait for it:
     - 9.1.e (`needs: 8.1, 8.3`, so parallel with 8.2) calls `invalidate(tags)`;
     - 11.3 (`needs: 1.2.b, 4.1.e`) tags its reads, and E28 needs `availability:<id>`;
     - 18.2.d (`needs: 1.2.g, 17.1`) dispatches to `invalidate(tags)`.

     Each would inline tag strings or wait on an unrelated task.
   - **The missing route.** `grep "x/revalidate" TASKS.proposed.md` finds nothing, yet both apps' mounts say `export { POST } from '@engine/http/legacy/unbuilt' // until WEB builds @engine/http/revalidate`. So the out-of-request path in E23 posts to a 404, and seed or MIG-import edits would never invalidate, with no error.

   **Fix.**
   - Move the package skeleton into 4.8, or a sibling SCH task in phase 4 or 5: the tag builders known today, `invalidate()`, and `next` as a **peerDependency** plus a devDependency, as cms declares it. Later lanes then add a builder on request.
   - Add a WEB subtask that builds `/api/x/revalidate` before the first out-of-request caller (18.2 or MIG). It should:
     - accept POST only;
     - require `REVALIDATE_SECRET` as a bearer, compared in constant time like `cron/auth.ts`;
     - take a body of tags, each checked against the builders' grammar;
     - take each tag's profile from its builder, never from the request;
     - answer `no-store` 204;
     - repoint both mounts in the same change.

   Give 9.1, 11.3 and 18.2 a `needs:` on the new task.

2. **should-fix (before the edits land)**. E23 (8.2.g), 8.2.e and 9.1.e. **`invalidate()` from an `afterChange` hook runs before the commit.** In Payload 3.90.2, `collections/operations/create.js` runs the `afterChange` hooks (`:388`) and `afterOperation` (`:403`) before `commitTransaction(req)` (`:421`).
   - A `revalidateTag` fired there can start a regeneration that reads the pre-commit row and caches it as fresh.
   - Under `'max'`, that stale entry stays until the next edit of that work. Under `{ expire: 0 }`, it lasts until the one-minute backstop.
   - A rolled-back save still invalidates, which is harmless.

   E23 also says "`revalidateTag` inside a Next request, else a post", but Next has no public "am I in a request" test, and E24 proves it with "unit tests", which cannot run Next's request store.

   **Fix.** 8.2.g states that invalidation runs **after commit**:
   - inside a request, schedule it with `next/server`'s `after()`, which runs once the response has been sent, and Payload's REST handler has committed by then (confirm against the installed docs that `revalidateTag` is allowed in `after()`);
   - outside one, collect the tags on `req.context` and let the caller flush them once its operation returns. MIG imports flush once per batch, not once per row.

   Name the detection mechanism, and prefer an explicit mode over probing Next's internals. Replace "(unit tests)" in E24 with a check on a production build: edit a work, request its page in the same second, and see the new value.

3. **should-fix (before the edits land)**. E21 (5.4.b) and §15 condition 3 (`ARCHITECTURE.md:652`). **The Payload fence only sees direct imports, and one package cycle is left open.** 5.4.b fences only `payload`, `@payloadcms/*` and `@engine/cms`. A handler that imports `@engine/loaders` (which reaches cms for its Local API reads) gets Payload statically, and so does any future package that depends on cms. SEO's sitemap, feeds and OG handlers, and MED's, are the natural candidates. Those handlers would then evaluate the Payload config in `next build`'s page-data pass and in route parity's runner, which is what condition 2 exists to prevent.

   There is also a latent package cycle. C2 has `Loaders.notFound` read C13's `PROXY_REQUEST_HEADERS`, and E27 has `loadItem` read `publicPath`/`publicSearch`, so loaders → `@engine/http`. If an http handler imports loaders, http → loaders, and §15 condition 4 covers only cms ↛ http.

   **Fix.**
   - Make the fence transitive: route parity's runner (5.4.a) loads every mount under a resolve hook that throws on `payload`, `@payloadcms/*` or `@engine/cms`. That permanent, behavioural check replaces the one-time clause in E15. Alternatively, have 5.4.b's rule list every workspace package whose `package.json` depends on `@engine/cms`, computed rather than hand-listed.
   - Record the loaders ↔ http rule in §15. I recommend that an http handler reaches content only through its own `payload-*.ts` module, never through `@engine/loaders`. The other option is to have the page pass `publicPath`/`publicSearch` to the loader as arguments, so loaders never import http (see #5).

4. **should-fix**. E15 (4.6.c Check), E16 (4.8.c), `ARCHITECTURE.md:672`. **"`DATABASE_URL` unset" does not mean "no database reachable".** `db/adapter.ts` passes `connectionString: env.DATABASE_URL`. When it is `undefined`, `pg` falls back to `PGHOST` and friends, then to `localhost:5432` as the OS user, which is the docker-compose Postgres on every workstation. So a stray connect during the build, or during 4.8.c's import test, could succeed or fail silently rather than being caught. "Outbound connections refused" also has to cover loopback.

   **Fix.** In both checks, point `DATABASE_URL` (and `PGHOST`/`PGPORT`) at a sentinel TCP listener and assert that it accepted **zero** connections. Or build inside `docker run --network none`, or under `unshare -rn`, where loopback has no Postgres. For 4.8.c, a spy on `pg.Pool.prototype.connect` is enough.

5. **should-fix (4.3's fix round)**. E3 (4.3.f), `DESIGN-SYSTEM.md:35-40`, MIGRATION.md §6, `view-models/src/loaders.ts:79`. **The docs are ahead of C2, and 4.3.f is breaking.** At 9055b3c, `Loaders.item` is still `(p: At & { publicId: number; slug: string })`. Meanwhile DESIGN-SYSTEM §2 and MIGRATION §6 already describe a loader that takes the id alone and reads the public path. The §2 sample passes `parsePublicId(idSlug)`, which returns `number | null`, into `publicId: number`, so it does not type-check. Removing a required parameter is breaking by CONTRACTS.md's own rule (an implementer that reads `p.slug`, or a caller that passes it, stops compiling), even though no lane implements it yet.

   **Fix.**

   - In the §2 sample, check `null` → `notFound()` before calling the loader.
   - State that the item's cached read is keyed by `(locale, publicId)` only. The public path and query are compared outside `'use cache'` and never become a cache argument: they are attacker-chosen, and each spelling would otherwise be a new cache entry. The spike's `resolveItem` already works this way.

6. **should-fix**. E21 (5.3.c), `manifest/proxy.ts:22-29`. **`x-public-search` copies capability tokens onto every request.** C13 says a pay-link or quote page reads its token **from the query** (`manifest.ts:34`, C10 `sensitive`). 5.3.c sets `x-public-search` on *every* request the proxy passes on. That puts the token into a request header that any server component can read, and that any header-capturing logger or error reporter would record. The rule "like any query string it is never logged" covers logged URLs, not dumps of request headers. The header's one use is the item route's 308.

   The part of the question about reflecting it into the page or into `Location` is sound:
   - WHATWG `search` is percent-encoded ASCII;
   - `Location` is `href()`'s root-relative path plus the query, so it cannot leave the origin;
   - React escapes it anywhere it is rendered;
   - the client's copy is always overwritten (`''` when there is none).

   **Fix.**
   - Set `publicSearch` only on the item route's rewrite, and `''` on every other request, where a client's copy is still dropped. At minimum, set it never on a `sensitive` page.
   - Add to C13 that error reporting scrubs `x-public-search`.
   - Add the rule that a handler under a path the matcher excludes (`/api/…`, `/brand-assets/…`) never reads `PROXY_REQUEST_HEADERS`: a client reaches those paths directly, so the headers there are the client's own.

7. **should-fix**. E21 (5.3.d), DEPLOYMENT.md §3/§8, `.env.example:62-72`. **Loopback `HOSTNAME`: the refusal is correct, but the check is written from a hand-made list.** Every standalone `server.js` reads `HOSTNAME` (`build/utils.js:1125`), and Next's rename makes any loopback literal hang. So refusing one is right on every host and in CI, where `start-server.sh` pins `0.0.0.0`.

   The listed spellings miss what Next actually matches. Next tests the WHATWG-normalised host, so `127.1`, `2130706433` and `0x7f.0.0.1` all normalise to `127.0.0.1` and hang, yet none is "in 127.0.0.0/8" as written. `::ffff:127.0.0.1` normalises to `[::ffff:7f00:1]`, which Next does *not* rename. Refusing it is harmless, but it is not the rule.

   On a workstation, `next dev` and `next start` ignore `HOSTNAME` and read `-H` instead (`cli/next-dev.js:216`, `cli/next-start.js:72`). So under `pnpm dev` the refusal rejects a value that has no effect. That is fail-closed and cheap to undo, so I would keep it. The check cannot see the real hazard there, `next start -H 127.0.0.1`, which hangs the same way.

   **Fix.**
   - Normalise first: `new URL(`http://${host.includes(':') && !host.startsWith('[') ? `[${host}]` : host}`).hostname`. Then apply Next's own test (`^127(\.\d{1,3}){3}$` or `[::1]`), and test the numeric spellings.
   - Word the finding so it names `server.js`, says that `next dev`/`next start` take `-H`, and says that a loopback `-H` hangs too. Add that sentence to `.env.example`.

   It cannot refuse a working standalone setup: `0.0.0.0`, `localhost` and host names all pass.

8. **should-fix**. `DEPLOYMENT.md:82-101` (the pm2 entry). **`HOSTNAME=0.0.0.0` puts the app port on the public interface.**
   - On Helios, 4030 and 4031 are then reachable over plain HTTP, bypassing nginx's TLS and its `X-Forwarded-For`. That matters because §7's in-process rate limits key on the client address, and a direct hit can forge it.
   - The entry also does not pin pm2's mode. 4.6's single-flight jobs run, §7's in-process rate limits and the ~5 s health memo are exact only with one process per brand. A CloudPanel or pm2 template running `-i max` would silently break all three.
   - `localhost` is the other value `.env.example` allows, but Node binds only the first address `getaddrinfo` returns, which is often `::1`. An nginx upstream at `127.0.0.1` would then get 502s.

   **Fix.**
   - Add to §3: `exec_mode: 'fork'`, `instances: 1`.
   - Add that the app ports are closed at the host firewall (CloudPanel's rules allow only 22/80/443), and that 5.1.a verifies it with a `curl http://<public-ip>:4030` from outside, expecting a refusal. This is HAR's and the owner's to apply on Helios (5.1.b, 👤), not decided here.
   - Prefer `0.0.0.0` over `localhost` in §8.

9. **should-fix (small)**. `ARCHITECTURE.md:592-599`, E40/E41, DEPLOYMENT.md §7. **Next's bare 500 on undecodable paths.** Setting it apart is right, but it is recorded only in ARCHITECTURE §13. DEPLOYMENT §7, the doc that defines the alert and which §13 cites, is unchanged.
   - "A 500 whose request path does not percent-decode" is not something Alloy or LogQL can evaluate: RE2 has no decode and no lookahead. A computable rule is `status = 500`, a path under `^/(brand-assets|api/x)/`, and the path containing `%`. No brand asset or engine API path legitimately carries one: brand-asset segments are `SEGMENT`-checked, and the public legacy URLs are logged under their public, proxied path.
   - Nginx probably answers malformed hex (`%A.`) with its own 400 first, which would leave only well-formed-hex, invalid-UTF-8 paths (`%C0%AE`, `%FF`) reaching Next. 41.2.c should measure this through CloudPanel's nginx.
   - Count these 500s as their own series (a ticket past a rate), never silently dropped, so a Next regression that 500s every `%` path still shows. E41 should also assert that a real 500 elsewhere still pages.
   - While editing §7: "payment provider reachability" in `/api/health` must be reported, never gating, like queue lag. A failed health check rolls a deploy back.
