## Findings

### S1 (should-fix): the cycle guard has a race, so two concurrent re-parents can store a cycle

`engine/packages/cms/src/collections/places/ancestry.ts:312-343` (`guardAncestry`) reads the chain at READ COMMITTED and takes no lock. Two saves that each look legal on their own can both commit.

**Repro (P7):** create published X and Y, then run `Promise.allSettled([update X {parent: Y}, update Y {parent: X}])`. Both are fulfilled, and the database then holds `x.parent = y` and `y.parent = x`.

The impact is any unbounded tree walk: the C10 path builder, the facet roll-up (16.3.b) and breadcrumbs. The data can be recovered (setting `parent: null` still passes).

**Fix:** serialise tree writes. Take `pg_advisory_xact_lock(<places-tree key>)` inside the operation's transaction before walking. Use `req.transactionID` and the adapter's session for that transaction, and add a db test that runs the swap concurrently. Separately, record that every reader caps its walk at `MAX_PLACE_DEPTH`.

### S2 (should-fix): the depth limit ignores the subtree being moved, which can leave a descendant permanently un-editable

`validators/place-ancestry.ts:59` checks only the depth of the place being saved. `ancestry.ts:307-310` (`proposedParent`) re-runs the whole check on every update, even one that doesn't change `parent`.

**Repro (P6):** build the chain L1›L2›L3›L4›L5, plus F with a child G. Move F under L5; that passes, with F at level 6. Then make any edit to G, such as `{type:'town'}`. It is refused: "The place hierarchy goes at most 6 levels deep; under this parent the place would be at level 7."

**Fix:** on a re-parent, refuse when `depth(newParent) + height(subtree) > MAX_PLACE_DEPTH`. Find the height by walking `parent = id` down, bounded by the limit. When `parent` is unchanged, check only for cycles, not depth.

### S3 (should-fix): the delete guard misses children that point at the place only in a draft, and that draft is then silently orphaned

`ancestry.ts:345-360` (`keepChildrenAttached`) counts only main-table rows (`payload.count` with no draft).

**Repro (P8):** create published P and C. Update C with `draft:true` and `{parent: P}`. Deleting P is allowed, and C's latest draft parent is now `null`. C would publish as a root, and its address would change.

**Fix:** also count the latest versions. That means a `payload.countVersions` / `db.count` on `_places_v` with `latest = true AND version.parent = id`. Or refuse when either view has children.

### N1 (nit): a hand-typed slug held only in a draft is invisible to the uniqueness check

`collections/terms/vocabulary/slug.ts:237-255` (`slugTaken`) counts main rows only.

**Repro (P5):** publish maker A, then save a draft of A with `slug:'gamma'`. Create maker B named "Gamma"; it gets `gamma`. Publishing A is then refused with a slug ValidationError.

No data is corrupted, and the error is clean. The only cost is that A's draft gets stuck. Optional: also check latest drafts.

### N2 (nit): parallel creates with the same name lose to the unique index with a generic error

`slug.ts:258-274`, check-then-insert.

**Repro (P4):** four parallel `makers.create({name:'Joan Blaeu'})` give `joan-blaeu`, `joan-blaeu-2`, and two `ValidationError: The following field is invalid: slug`. For three parallel terms, two fail with "invalid: kind, slug", because the compound index blames both columns.

Integrity holds. Note it for the migration importer and the seed: create per collection in series, or retry on a slug conflict.

### N3 (nit): `translationStatus` is public

`collections/terms/vocabulary/fields.ts:74-82`. It's an editorial workflow flag and appears in the public REST payload (P9). Consider `STAFF_ONLY_ACCESS` on it. No view model needs it.

### N4 (nit): required fields carry no `required: true`

`places.name` and `terms.label` are required only through custom `validate` (`requiredInDefaultLocale`), not `required: true`. The admin shows no required marker. That's acceptable, because `required` would block blank saves in the `id` locale. A description line would help editors.

### N5 (nit): shared vocabulary helpers sit inside `terms`

The helpers (`access`, `fields`, `slug`) live in `collections/terms/vocabulary/` and are imported by makers, places and sources. The implementer already flagged this. SCH should promote them to a shared `fields/` module before 8.2/9.x copies the pattern.

### N6 (nit): test support sits in `src/collections/places/`

`pushed-database.ts` is safe today, but a `src/test-support/` (or `*.test-support.ts`) location would make "never import from runtime code" lintable.

## For 8.2 (Works), not defects

- A reference-safe delete is missing for makers, terms and sources. Today a delete by admin or manager would let Payload's `_rels` FKs silently drop a work's maker credit, grade or reference. 8.2 should add a `beforeDelete` "still referenced by N works" guard, or ask 8.1's owner to.
- Shapes 8.2 can use as they are:
  - `MAKER_ROLES` in `collections/makers/roles.ts`;
