## Findings

1. **should-fix (docs; my own 4.1 #6 wording)**: the rewritten Suspense rule leaves no way to buy without JavaScript.
   - What the docs say:
     - "Only slow or live reads (availability, a live price, cart totals) stream inside `<Suspense>`, and a streamed part holds no form" (`CONVENTIONS.md:271-283`, `ARCHITECTURE.md:368-378`, `AGENTS.md:42-44`, `DESIGN-SYSTEM.md:55-59`).
     - "No purchase control renders before availability is known" (`DESIGN-SYSTEM.md:346-349`).
     - "What a visitor without JavaScript must … act on is resolved, never streamed: a form" (`DESIGN-SYSTEM.md:194-199`).
   - Why they contradict: an add-to-bag, reserve or hold button is a form, and each depends on availability. All three rules together mean the purchase panel's controls can never be in the first flush, so a JavaScript-off visitor can never buy. The spike never tested this, because its panel carried no form.
   - Fix: availability is the purchase-deciding read. It is live and one indexed read, which is the architect's own argument (`ARCHITECTURE.md:379-384`), so read it in the page body and render the purchase controls in the first flush. That also makes "never flashes" trivially true. Only reads that are slow for real, such as a courier quote or a remote FX rate, stream into the reserved placeholder. The alternative is to state that buying needs JavaScript and add it to DESIGN-SYSTEM §7.
   - Where: the four doc sites above and E28 (11.3.f). Before phases 30 and 33.

2. **should-fix (E28 11.3.f, `CONVENTIONS.md:288-293`, `ARCHITECTURE.md:385-389`)**: nesting defeats the one-minute backstop.
   - The problem: an explicit outer `cacheLife` wins over inner ones. A listing loader under `'use cache'` + `cacheLife('max')` that renders a card's *Sold* or *on hold* from the availability-status read therefore keeps that status for the listing's own lifetime (`cacheLife.md:406`). Inner tags still reach the outer entry, so an `{ expire: 0 }` write does expire the listing. But the backstop exists for exactly the cases with no write: a missed invalidation, or a lock or hold lapsing at `expiresAt`. A lapsed hold on a cached catalogue page would read *on hold* until something else invalidates it.
   - Fix: a cached scope that shows an availability status declares the backstop as its own explicit `cacheLife`. Or the status is read in its own cached function outside the content's scope, and the two are merged at render.
   - Also: export the one backstop value from `@engine/cache` (8.2.g, E23), beside the tag builders that already carry each tag's expiry, rather than from a loader.
   - nit: `cacheTag()` drops tags past 128 in one call with only a console warning. A listing that tags each card's `availability:<id>` batches its calls, or a large page silently loses invalidation.

3. **should-fix (docs, C2 note)**: "Next hands one param two ways" is true of every param, not only the item route.
   - Evidence: measured on a plain `[slug]` page, direct and through a rewrite. The page gets `caf%C3%A9` and `generateMetadata` gets `café`.
   - Why it matters: 4.3 settles only the item route, which reads only the id (`DESIGN-SYSTEM.md:48-54`, `MIGRATION.md:213-217`). But `Loaders.design`, `page`, `maker` and the `Indexed` surfaces take `slug` (`view-models/src/loaders.ts:71,80,92`). A route that passes `params.slug` to its loader from both the page and `generateMetadata` looks the record up under two strings. With Dutch or Indonesian names, a non-ASCII slug is likely, and then either the body or the metadata misses.
   - Fix, in CONVENTIONS §12 and a C2 line on slug inputs: a route never hands a raw `params` segment to a loader or compares it. It decodes it once through C10 (`decodeSegments`), or the loader takes C10's parse of the public path. Loader slug inputs are decoded. Add a two-spelling case to 22.4.c's route-map smoke test.

4. **should-fix (E32 22.7.d; `config/src/routes/parse.ts:160-165`)**: carrying an undecodable slug "as asked for" turns 404 into a bare 500.
   - Evidence: a rewrite to `/<locale>/item/1706-%FF` or `…-caf%E9` fails Next's param decoding and answers `500 Internal Server Error`, logged nowhere. The same link rewritten to the id alone answers the one 308 and keeps the query.
   - Fix: for a slug part that does not decode, C10 hands the item route the canonical id with a fixed never-matching ASCII slug, or the id alone. The route reads only the id anyway, and the public path still carries what was asked.
   - 22.7.c's Check adds a production-build probe to the status spec: `/product/1706-%FF` and `/product/1706-caf%E9` answer 308, not 500. Also add this 500 beside the undecodable-path note in ARCHITECTURE §13 and 41.2.c (E40).

5. **should-fix (E29 22.4.e, `DESIGN-SYSTEM.md:100-108`)**: two conditions the NotFound decision rests on.
   - (a) Metadata. Under a 404 status Next resolves metadata from the `not-found` boundary, never from the page. So the designed NotFound's title and description, localised, come from `(site)/[locale]/not-found.tsx`'s `generateMetadata`, and the not-found page exports none. `noindex` is automatic.
   - (b) Ordering. Once 22.4.e stops the page from calling `notFound()`, its 404 depends entirely on 5.3.a and 5.3.b. Without a User-Agent it was 200 even on a ƒ route, as measured. 22.4 needs `11.3, 22.1–22.3, 22.7` and nothing in its chain reaches phase 5, so add **5.3** to 22.4's needs. The status spec (5.4.e) would catch the soft 404, but the dependency should be declared.
   - Note for 22.4: a client navigation to a proxy not-found costs two requests (RSC 404, then a document load). That is acceptable.
   - Claim verified: yes. Rewrite status 404, the designed body, `lang`, the forms and the streamed parts all arrive, and the status survives the render (`resolve-routes.js:375`, `app-page-runtime.js:1211`). It is implementation behaviour, not a documented promise, so 5.4.e should also assert the not-found body (a non-empty `<main>`) once 22.4.e lands, not only the 404.

6. **should-fix (E25 11.1.c, 5.4.c; `AGENTS.md:46`, `ARCHITECTURE.md:357-360`)**: `next/link` is not the only prefetcher.
   - `next/form`'s `<Form>` prefetches its action path whenever it is visible, by default. A header search form would cost a full render of `/search` on every page view under `htmlLimitedBots`. `useRouter().prefetch()` would too.
   - Fix for 5.4.c: fence `next/form`, or require `prefetch={false}`, fence `router.prefetch`, and cover every package that renders storefront JSX, not only `ui`. The primitive's props type omits `prefetch`.
   - AGENTS.md and ARCHITECTURE still read "`<a>` or `<Link prefetch={false}>`", which a developer takes as licence to write the `Link` directly, and 5.4.c will reject that. Say "an `<a>`, or the link primitive (11.1)".

7. **should-fix (5.4)**: the "one segment config" rule has no guard.
   - The gap: Cache Components rejects `dynamic`, `revalidate` and `fetchCache` at build. It accepts `prefetch = 'partial'` (documented as working only under Cache Components), `runtime`, `preferredRegion`, `maxDuration`, and an `instant` on any other segment. Removing `instant = false` fails the build, which is good, but it lives in UXG's and UXE's layout files, where 5.4.d's config-parity test does not look.
   - Fix, an ESLint rule in 5.4.b: no route-segment-config export under `engine/apps/*/src/app/**` except `instant = false` (and `generateStaticParams`) in `(site)/[locale]/layout.tsx`, proven by a planted violation. 5.4.d asserts both layouts export it.

8. **should-fix (E3 4.3.f, E27 11.3.a; `view-models/src/loaders.ts:79`, `DESIGN-SYSTEM.md:40`)**: `Loaders.item` still takes `{ publicId; slug }`.
   - The gap: DESIGN-SYSTEM's sample already calls `loadItem({ locale, publicId })`, and the v1.3 changelog says nothing about it. 4.3.e's "C2 … at v1.3 with a changelog entry" is therefore not met until 4.3.f lands.
   - I agree with dropping `slug`: the route reads only the id (#3).
   - Change the shape: instead of the loader reading the C13 headers itself, make the asked-for address an explicit input, `{ locale, publicId, asked: { path, search } }`. The page reads `x-public-path` and `x-public-search` and passes them in. The loader then stays a pure function, testable against fixtures without a request scope, and its `'use cache'` half never sits beside a `headers()` call.
   - The changelog line: an input change, with no loader, fixture or caller built (`LoadItem` has no implementer), so no lane breaks.

9. **nit (C2, `view-models/src/shell.ts:49-51`)**: `touchIcon?` and `manifest?` are optional only for 4.1's interim shell, and 4.6.e (E14) moves that shell to set both. After that nothing needs `undefined`, but no task tightens the type, so three states (absent, `null`, a URL) would stay forever. Add "both required" to 11.3.a, or to ARC at 4.6's merge. It is a C2 minor bump that affects producers only.

10. **nit (5.3.c)**: `publicSearch` is clean only because Next strips `_rsc` before the proxy runs. `skipProxyUrlNormalize` (`__NEXT_NO_MIDDLEWARE_URL_NORMALIZE`) would switch that off, and then a stale slug's 308 would carry `_rsc` into the visible URL. Add a unit test that `_rsc` never reaches `publicSearch`, and a line saying `skipProxyUrlNormalize` stays off.

11. **nit (C13 `FORM_RESULT`, `manifest/forms.ts:55-70`)**: the result shows "only on the page it returns to", compared by public path. A page whose state is in its query, such as search results or a filtered listing, returns without it. Now that `publicSearch` exists, decide whether `returnTo` is the path plus C10's canonical query or the path alone, and say the comparison is by path.

12. **nit (`ARCHITECTURE.md:346-348`)**: "serves it the shell's 200" is not the whole cause. A request with no User-Agent also lost the proxy's 404 on a route the build lists as ƒ. C13's comment is right ("a 404, a permanent redirect and `PROXY_NOT_FOUND_STATUS` are all lost"), so use its wording.

## Agreed, no action

- **`instant = false` and `htmlLimitedBots`** (AGENTS.md, CONVENTIONS §12, ARCHITECTURE §9): correct and complete. That includes the costs I listed in 4.1, and the rejection of `prefetch = 'force-disabled'`, which the installed doc confirms still prefetches route metadata and is a second segment config.
- **NotFound without JavaScript**: verified (see #5). DB-decided misses keep `notFound()` and accept a client-rendered body. That is the right trade, because a route handler cannot render app components.
- **`x-public-search`**: sound. It survives the rewrite and reaches a client navigation's redirect without `_rsc`, and `URL.search` is already percent-encoded, so no header injection is possible. Scoping it to "only a permanent redirect carries it" is right.
- **`FORM_RESULT` — "no Fetch Metadata counts as a document navigation" is safe.**
  - The cookie is `Secure`, and browsers send `Sec-Fetch-*` to every potentially trustworthy origin. So any modern browser that carries the cookie also sends Fetch Metadata.
  - The browsers that send none are Safari before 16.4 and very old Chromium or Firefox. Even there, the only request that can reach the `returnTo` page before the visitor sees it is the 303's own document GET, which should consume it.
  - The failure mode is a lost confirmation, never a leak: the id is opaque, `HttpOnly`, `SameSite=Lax`, and bound to its page. Failing closed instead would re-show the result, including a failed post's entries, on every reload for ten minutes.
  - Fetch Metadata is also the only signal a page has, because Next hides the RSC flight headers from `headers()`. Record that beside the rule, so nobody "improves" it with the `RSC` header.
  - `Sec-Purpose: prefetch;prerender` is excluded, which is right.
- **`PROXY_USER_AGENT`** (`engine-proxy (no user-agent)`): non-empty, since Next treats `''` as none. It matches `/.*/` and no real client, and it is set only when the header is missing or empty. It is load-bearing for `PROXY_NOT_FOUND_STATUS` too (measured), which 5.3.e checks.
- **The 308 wording** (E33–E38, MIGRATION §6, C10): correct. The URL gate's "at most one normalising 308, recognised by its `Location`" is exactly what Next does before the proxy.
- **One e2e folder, `tests/e2e/`**, and **HAR owning each app's `next.config.ts`, `tsconfig.json` and `package.json`**, with a parity test: agreed. The status spec imports only `@playwright/test`, so the move is mechanical.
- **5.3** (PLT: UA, 404 status, `publicSearch`, loopback `HOSTNAME`) is right-sized, and its Check probes a production build without a UA. **5.4** (HAR gates) is six subtasks of mechanical tooling and fine for a medior once #6 and #7 are folded in. **11.1.c**, **11.3.a/f**, **22.4.e**, **22.7.d** and **33.3.a** are right-sized, subject to #1–#5 and #8.
